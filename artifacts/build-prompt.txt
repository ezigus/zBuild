### zBuild — Vision

> The North Star for zBuild — it steers how zBuild is built. The README distills it; the wiki references it; every pipeline run is steered by it.

#### Intent
zBuild turns a delivery process into data — templates and plugins — so software is built the same disciplined way every time. We build zBuild the way zBuild builds: a minimal core, with all behavior plugin-delivered and template-composed. A good change is small, aligned to the spec, proven by a test, and wired into the live path — never scaffolding that looks finished but does nothing.

#### Principles
- **Target-agnostic by contract** — zBuild builds *any* repository, not itself; the engine and plugins never assume the target's language, layout, or that zBuild is the target. Target knowledge lives in data — templates, config, per-repo overrides — never in code.
- **Spec wins over drift** — KEEPERS, ARCHITECTURE, and the ADRs are the source of truth; when code disagrees, the code changes, not the spec.
- **Small engine, behavior at the edges** — keep the core tiny; add capability as plugins composed in templates, never by growing the engine.
- **Safety is structural** — all model-bound text passes one redaction chokepoint; state is atomic and resumable; scope is governed at every boundary.
- **Models are data, not code** — selection flows through the router and config tiers; never hardcode a model name.
- **Prove behavior, then wire it** — every change ships a test that fails without it and connects to the live path; green-but-inert is a defect.
- **Fail closed, never silent** — gates block on real problems and say why; bounded cycles and recovery drive work to done.
- **Dogfood every change** — build zBuild with zBuild; if the pipeline can't ship it, fix the pipeline.

### Rules
These are this repository's rules (.zbuild/prompts/rules.md). Work that
breaks one is wrong, whoever wrote it.

- Bash only, and match the file you are in: 4-space indent, LF line endings, a final newline, no trailing whitespace (.editorconfig). Everything must pass `shellcheck` with the repo's .shellcheckrc.
- Never pipe anything into `grep -q`, and never pipe into a bare `head`, in any `.sh` file, test files included. The reader exits early, the writer takes SIGPIPE, and under `set -o pipefail` the line fails for a reason nothing logs. Use a here-string instead: `grep -q PATTERN <<< "$var"`, or run grep on the file directly: `grep -q PATTERN "$file"`. `tests/unit/sigpipe-antipattern-guard-test.sh` fails the suite on any violation; a genuinely safe pipe is annotated `# sigpipe-ok: <reason>`.
- Never name a model (haiku, sonnet, opus, …) in code; model selection goes through core/router and config/models.json.
- A test must be able to fail: assert what is required, never what the code happens to do.
- Never edit anything under `legacy-DoNotUse/`.

#### Facts about this repo
- `ZBUILD_*` environment variables are set by the engine at dispatch (the artifact dir, the stage's input index `ZBUILD_STAGE_INPUTS`, the issue, the run). They are trusted engine inputs, not user or attacker input.
- A stage never names another stage's output — not its output name, not its file. The engine hands every stage every earlier stage's latest output, and a stage finds what it needs by what it contains (scripts/lib/earlier-output.sh; ADR-055 §1). A plugin that names another stage's output is a defect.
- Every stage writes a v2 result (`result_contract`, `verdict`, `disposition`, `reason`, detail under `data`) on every exit path, and exits 0 or 1 (ADR-054).
- `[SPEC-n]` / `[#<issue>/SPEC-n]` tags in a test tie an assertion to one issue's acceptance contract. A tag that belongs to another issue must never be changed or removed.

## What you own

Your job is to edit the working tree to make the code do what the
design's steps below decide. You have Read, Edit, Write, and Bash tools available.

### How you write the change
- Make the code do what was decided for it, no more and no less:
  the simplest change that makes every requirement's test pass, and that
  handles the edge cases the requirements name.
- When what was asked and what the code can do differ in a way you cannot
  close, say so in your answer rather than building something else.
- When a test fails, find out why it fails before you change anything else.

### How your work is kept
- You make code changes via Edit/Write/Bash. What you change stays in the
  working tree: if you do not finish, the next try continues from it, and your
  notes file (in the rules below) carries what you learned.
- Write your notes file first, and add each thing you find to it
  before your next step. If you are cut off, your notes are what the next try
  starts from.
- Do NOT emit a unified diff in your response — the pipeline derives the
  canonical `diff.patch` artifact from `git diff HEAD` automatically.

### Saying you are done
Emit `LOOP_COMPLETE` on its own line as the FINAL line of your response
WHEN the implementation is complete — whether you just finished it OR
it was already done before you started. If the branch already contains
the required changes (check `git log` for commits + `git diff` for any
remaining gap) AND no stage under Previous work has failed findings left to
answer, emit `LOOP_COMPLETE` immediately. Do NOT keep iterating when there is
nothing left to do. Every finding you are given is answered, each on its own
line before the sentinel: `done` (you changed something for it), `wrong`
(it does not hold, and why) or `not mine` (your job cannot fix it, and why).
A finding with no answer stays open, and is shown to you again.

### When a finding does not reproduce
If a failing stage names a test and that test PASSES when you run it on this
tree, say so and stop. Answer that finding, on its own line before the sentinel:

    ANSWER <the finding as listed>: wrong — not reproduced: <the path you ran>

one line per finding. This is a REPORT, not a verdict: the pipeline re-runs the
stage that raised the finding to check. Do not keep searching for the cause of
a failure you cannot produce, and do not change code to chase one.

### When a test is wrong
If a test fails on code that already does what its requirement says — the test
itself cannot pass — do not change the code to chase it; you may not change the
test. Answer that finding as soon as you are sure, on its own line before the
sentinel, and stop working on that test:

    ANSWER <the finding as listed>: wrong — the test is wrong: <test file>: <why>

Say exactly why it cannot pass. The stage that owns the tests is given this
answer, and fixes the test.

### When a test should change
If a test checks behaviour this change is meant to alter — it pins the old
output, value or rule — the test must change, and the stage that writes the
tests changes it. Answer its finding, on its own line before the sentinel:

    ANSWER <the finding as listed>: not mine — the test must change: <test file>: <why>

Say what the test pins and what the change makes it.

You know a test is wrong by a check, not by a feeling. If the test fails the
same way with your change set aside (git stash), your change did not cause it:
find what in the test makes it fail, give that answer, and stop.

### When a test leaves something behind
A test that leaves something behind — an exported variable, a file outside its
own folder, a background process — breaks the tests after it. Which of three it
is decides what you do:
1. Your code puts it where it should not: change the code to write where it is
   told (TMPDIR, HOME, or a folder the caller passes in).
2. The code is meant to leave it, and the test does not clean it up: you may
   not change the test. Answer, on its own line before the sentinel:

    ANSWER <the finding as listed>: wrong — the test is wrong: <test file>: needs cleanup of <what>

3. Every test needs the same guard: it belongs in the shared test helpers,
   which are in the test folders — answer the finding `not mine — the test
   must change: <helper file>: needs <the guard>`.

### Running tests
- Do NOT run `npm test`, the full suite, or `npm run lint` — the pipeline
  runs them and their results are under Previous work.
- Start from the test files listed under Previous work, and the requirements
  each covers. Run a test file only to see whether a failure still holds
  (below) or after you change the code it checks, and only that test file. A
  command that runs longer than ~2 minutes can cost you the whole call.
- A failed stage under Previous work shows what failed when that stage ran; the
  code may have changed since, so run that one test file once, before you work
  on it, to see whether it still fails, and start from the failing line it shows.

### Data another part of the code writes
When your change reads data that another part of the code writes — a file, a
record, a field, a message — open the code that writes it and use the names
and shapes it really produces, and when it produces them; never assume them.

### Commit message (#608)
Before the final `LOOP_COMPLETE` line, emit a single line of the form:

    COMMIT_SUMMARY: <one-line description of this iteration's change>

Keep it under 72 characters, present tense, imperative mood (e.g.
"add foo parser" not "added"). The pipeline uses this as the git commit
message for the per-iteration commit it creates on your behalf. If you
omit this line the pipeline falls back to the design's title.

### Answering each design step
Before the sentinel, answer every one of the design's steps, by its number, each on its own line:

    step N: done — QUOTE: <file> | <a line this change added>
    step N: not needed — <why>

- `done`: you did what the step says. Quote the line this change added that does it, in a file in that step's areas, copied as it is with no quote marks. It is checked: a line this branch did not add, a file outside the step's areas, or a line that does not do what the step says sends you round again for that step.
- `not needed`: the code already does what the step says, or the step is wrong; say why.
- A step with no answer is not done, and you are sent round again for it.

# Design — GitHub label claim (#1764)

## Goal

Prevent two concurrent zBuild runs on the same issue from overlapping across machines using a
GitHub label (`zbuild:claimed`) as a soft cross-machine claim. The existing local flock
(`core/state/issue-lock.sh`) remains for intra-machine serialisation; this change adds the
inter-machine layer on top of it.

## Context

`core/state/issue-lock.sh` is a filesystem flock: effective on one host, invisible from another.
Issue #1764 asks for a GitHub label that any run can see before it starts. The run-status sidecar
already posts a progress comment on the issue (ADR-064, `scripts/lib/run-status-comment.sh`);
the holder string goes into that comment, satisfying RQADR-2 without a separate claim comment.

## Decision

**Run-status comment as the progress comment.** `rsc_render_header` (in `scripts/lib/run-status-render.sh`)
adds a machine-readable `<!-- zbuild-holder: ... -->` HTML comment immediately after the
`<!-- zbuild-run-status run_id=... -->` marker line. Format:
- CI (`GITHUB_ACTIONS=true`): `<!-- zbuild-holder: ${GITHUB_SERVER_URL}/${GITHUB_REPOSITORY}/actions/runs/${GITHUB_RUN_ID} -->`
- Local: `<!-- zbuild-holder: run_id=<run_id> machine=<hostname> -->`

**Amend `plugins/claim-coordinator/github-labels/plugin.sh`** (the existing plugin owns this job):
- Change `claim_coordinator_claim` to use the single shared label `zbuild:claimed` instead of
  `claimed:<machine>`. Delete the `local our_label="claimed:${machine}"` line and all per-machine
  label logic from both `claim_coordinator_claim` and `claim_coordinator_release`; replace with
  `local label="zbuild:claimed"`. The simplified check: if `zbuild:claimed` is absent, add it;
  if present, search the issue's comments for the most recent run-status comment and extract the
  `<!-- zbuild-holder: -->` line into a returned holder string.
- Change `claim_coordinator_release` to remove `zbuild:claimed` (no machine suffix).
- The `_ccgl_*` backend helpers remain and are used by the amended public functions.
- `plugin.sh` MUST NOT contain any `source` of `core/claim/claim.sh` — that creates a circular
  dependency (`claim.sh` sources `plugin.sh`; a reverse source closes the loop) and adds a
  startup `$(cd ...)` subshell on plugin.sh's load path. The dependency arrow is one-way:
  `claim.sh` sources `plugin.sh`.

**Update `plugins/claim-coordinator/github-labels/README.md`**: remove all references to
`claimed:<machine>` labels; describe the single shared label `zbuild:claimed`; update the
`ZBUILD_CLAIM_MACHINE_ID` env-var row to note it is now used only for the holder string in the
run-status comment, not in the label name.

**New `core/claim/claim.sh`** (thin wiring bridge — no reimplemented logic):
- Sources `plugins/claim-coordinator/github-labels/plugin.sh` using `$_ZBUILD_ROOT` (already
  set by runner.sh before claim.sh is sourced) — not via a `$(cd ...)` subshell.
- `zbuild_claim_build_holder`: builds and exports `_ZBUILD_CLAIM_HOLDER`; uses `${HOSTNAME}`
  (bash built-in variable) for the machine name — never calls the external `hostname` command.
- `zbuild_claim_acquire <issue>`: skip if issue is empty; calls `_ccgl_read_labels` / `_ccgl_add_label`
  / `_ccgl_read_holder` from the loaded plugin; on conflict, sanitizes the extracted holder string
  (strip ANSI escape codes and literal backslash sequences via `printf '%s'` or `sed`) before
  storing in `_ZBUILD_CLAIM_HOLDER`, then returns 1; on success, sets `_ZBUILD_CLAIM_ACQUIRED`
  and returns 0. Backend errors (read or add failures) return 0 (graceful) and log a warning to
  stderr so the skip is visible in the run's output.
- `zbuild_claim_release <issue>`: skip if issue is empty or `_ZBUILD_CLAIM_ACQUIRED` is unset;
  MUST call `unset _ZBUILD_CLAIM_ACQUIRED` BEFORE calling `_ccgl_remove_label` (advisory).
  Unsetting first makes a second call a no-op — this is the idempotency guarantee DSCLA-13
  relies on.

**Wire into `core/pipeline/runner.sh`**: source `core/claim/claim.sh` at top (alongside
`core/state/issue-lock.sh`); call `zbuild_claim_build_holder` before the sidecar spawn so the
sidecar inherits `_ZBUILD_CLAIM_HOLDER`; call `zbuild_claim_acquire` right after
`zbuild_issue_lock_acquire` succeeds; on return 1, emit `pipeline.refused.claimed`, print holder
using `printf '%s\n'` (not `error()`, which uses `echo -e` and would interpret escape sequences
in an attacker-controlled holder string), then return 1 (same shape as issue-lock refusal); call
`zbuild_claim_release` in `_runner_abort_trap` after `zbuild_issue_lock_release`, using `declare
-F` guard. The call is placed AFTER the `trap '' INT TERM` guard already at the top of
`_runner_abort_trap`, which blocks SIGTERM re-entry for the duration of cleanup — this is what
RQCLA-11 relies on. `zbuild_claim_release` also unsets `_ZBUILD_CLAIM_ACQUIRED` on first call,
so a second invocation from any path is a no-op.

The EXIT trap is installed well after `zbuild_claim_acquire` succeeds; two early-failure return
paths between them (`_runner_enter_worktree` failure and `zbuild_run_branch_setup` failure)
currently call only `zbuild_run_cap_release || true` before returning. Both paths MUST also call
`zbuild_claim_release || true` and `zbuild_issue_lock_release || true`, mirroring the
`zbuild_run_cap_release || true` pattern already in those paths.

**Register `pipeline.refused.claimed`** in `config/event-schema.json` (follows pattern of
`pipeline.refused.issue_locked`).

**Register `core/claim/claim.sh`** in `config/shape-change-paths.txt`.

**Amend ADR-005** per RQADR-1 through RQADR-4. The existing §1 Enforced by bullet lists
DSCLA-1,5,6,7 but omits §1(c) — refused behavior. Extend it to add:
- `claim-coordinator-unit-test.sh [DSCLA-3]` (non-zero exit, no stage dispatched, event emitted)
- `teardown-repeat-signal-test.sh [DSCLA-9]` (refused output names holder)

The §2 Enforced by bullet also needs `[DSCLA-12]` added alongside `[DSCLA-2]` for the CI
holder rendering case.

**Amend ADR-059 §4** noting cross-machine exclusion is the coordinator's job per RQADR-5. The
`## Enforced by` section must gain a new entry for the §4 cross-machine statement, naming
DSCLA-3 as the enforcing test. CLAUDE.md requires a test per new/changed statement.

The label `zbuild:claimed` contains no hostname. Holder string contains machine name (local) or
CI URL — in the comment body, not the label (RQLAB-2). Check-then-label is not atomic at GitHub;
two racing machines may both succeed. Known limitation; a strict mutex is out of scope (RQMECH-1,
RQMECH-2).

Startup process budget: `source` builtins (no forks); `${HOSTNAME}` bash built-in (no fork);
no `$(cd ...)` subshells on the load path. Net startup-process cost: 0.

## What you must not do

The acceptance testfiles listed above are read-only for this stage, as is every file in the test folders: a change to them is put back. They are the contract you implement against, written before your implementation existed. When an assertion fails, fix your code. If it fails the same way with your change set aside, the test is wrong: answer as "When a test is wrong" says, and do not edit it. You MUST NOT weaken, delete, retag or re-author any assertion.

### The files you may change
You may change any file outside the test folders (tests/*, plugins/*/*/tests/*), and none inside them. Every file in the test folders — a test, a fixture, a test helper — belongs to the stage that writes the tests: a change you make there is put back.

### Rules
- Do not run `git commit` — the pipeline owns commit semantics.
- NEVER run a command that mutates git branch state or the working tree —
  no `git checkout -b`/`switch`/`commit`/`push`/`tag`/`reset`. You are running
  INSIDE the pipeline's own checkout; switching or creating a branch hijacks the
  run. The pipeline owns the branch.
- If you must exercise a command you are building (or any command that could
  publish, tag, push, or otherwise mutate state), run it in `--dry-run` mode.
  Do everything you can to verify behavior without side effects.
- Keep changes minimal and aligned with the design: change what the task needs.
- Clean up scratch siblings of the files you edit (`*.bak`, `*.orig`,
  `*.rej`, `*.head`, `*.tmp`, `*~`). `sed -i.bak` and
  `git show HEAD:f > f.head` both leave one behind — prefer `sed -i` with no
  suffix, and delete any comparison scratch before you finish. A new scratch
  file is removed for you; every other file you leave is part of your change.

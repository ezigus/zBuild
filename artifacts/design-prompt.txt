### zBuild — Vision

> The North Star for zBuild — it steers how zBuild is built. The README distills it; the wiki references it; every pipeline run is steered by it.

#### Intent
zBuild turns a delivery process into data — templates and plugins — so software is built the same disciplined way every time. We build zBuild the way zBuild builds: a minimal core, with all behavior plugin-delivered and template-composed. A good change is small, aligned to the spec, proven by a test, and wired into the live path — never scaffolding that looks finished but does nothing.

#### Principles
- **Target-agnostic by contract** — zBuild builds *any* repository, not itself; the engine and plugins never assume the target's language, layout, or that zBuild is the target. Target knowledge lives in data — templates, config, per-repo overrides — never in code.
- **Spec wins over drift** — KEEPERS, ARCHITECTURE, and the ADRs are the source of truth; when code disagrees, the code changes, not the spec.
- **Small engine, behavior at the edges** — keep the core tiny; add capability as plugins composed in templates, never by growing the engine.
- **Safety is structural** — all model-bound text passes one redaction chokepoint; state is atomic and resumable; scope is governed at every boundary.
- **Models are data, not code** — selection flows through the router and config tiers; never hardcode a model name.
- **Prove behavior, then wire it** — every change ships a test that fails without it and connects to the live path; green-but-inert is a defect.
- **Fail closed, never silent** — gates block on real problems and say why; bounded cycles and recovery drive work to done.
- **Dogfood every change** — build zBuild with zBuild; if the pipeline can't ship it, fix the pipeline.

### Rules
These are this repository's rules (.zbuild/prompts/rules.md). Work that
breaks one is wrong, whoever wrote it.

- Bash only, and match the file you are in: 4-space indent, LF line endings, a final newline, no trailing whitespace (.editorconfig). Everything must pass `shellcheck` with the repo's .shellcheckrc.
- Never pipe anything into `grep -q`, and never pipe into a bare `head`, in any `.sh` file, test files included. The reader exits early, the writer takes SIGPIPE, and under `set -o pipefail` the line fails for a reason nothing logs. Use a here-string instead: `grep -q PATTERN <<< "$var"`, or run grep on the file directly: `grep -q PATTERN "$file"`. `tests/unit/sigpipe-antipattern-guard-test.sh` fails the suite on any violation; a genuinely safe pipe is annotated `# sigpipe-ok: <reason>`.
- Never name a model (haiku, sonnet, opus, …) in code; model selection goes through core/router and config/models.json.
- A test must be able to fail: assert what is required, never what the code happens to do.
- Never edit anything under `legacy-DoNotUse/`.

#### Facts about this repo
- `ZBUILD_*` environment variables are set by the engine at dispatch (the artifact dir, the stage's input index `ZBUILD_STAGE_INPUTS`, the issue, the run). They are trusted engine inputs, not user or attacker input.
- A stage never names another stage's output — not its output name, not its file. The engine hands every stage every earlier stage's latest output, and a stage finds what it needs by what it contains (scripts/lib/earlier-output.sh; ADR-055 §1). A plugin that names another stage's output is a defect.
- Every stage writes a v2 result (`result_contract`, `verdict`, `disposition`, `reason`, detail under `data`) on every exit path, and exits 0 or 1 (ADR-054).
- `[SPEC-n]` / `[#<issue>/SPEC-n]` tags in a test tie an assertion to one issue's acceptance contract. A tag that belongs to another issue must never be changed or removed.

#### Rule ABS — a closed set breaks by omission

Some closed sets in this repo break by OMISSION rather than by a stale token you
can grep: the breakage is a MISSING (or orphaned) line, not a changed one. When a
change grows, shrinks, or renames such a set, every enumeration of that set is
wrong by omission — yet there is nothing to grep for, because the defect is the
absent entry. The pipeline's stages are not such a set: which stages run is
template data, not a list the code enumerates.

When a change grows, shrinks or renames a closed set, the design accounts for
every place that enumerates or COUNTS it:

- code or config that enumerates it: a step, naming that code;
- an existing test that enumerates or counts it: a line in the ```supersedes
  block (the test file, the assertion's tag, and why it is now wrong), so the
  test author brings it up to the new set.

Rediscover the places each time; a hardcoded list of them goes stale.

#### How to find them

Enumeration/count sites are most often mock-plugin roster blocks (one call per
member) or literal counts of the set. Rediscover them with:

```
grep -rln '_make_plugin\|_make_role_plugin\|_make_verdict_plugin\|mock_plugin_factory' tests/
grep -rln 'stage\.complete\|plugin\.run\.start\|started .*UTC\|finished .*UTC' tests/
```

Re-run the greps each time — new enumeration sites arrive with new tests, and
the defect (a missing line) leaves no token to search for.

#### Rule ABS-W — a new plugin directory needs a wiki page

A change that creates `plugins/<kind>/<id>/manifest.yaml` also creates
`docs/wiki/plugins/<id>.md`, with a prose opening paragraph: a step names it,
and a `[doc]` SPEC says what it must tell a reader. The `lint-doc-freshness`
gate (`scripts/lib/lint-doc-freshness.sh`) fails the suite when the page is
absent or has no opening paragraph — there is no old value to grep for, because
the defect is the missing new file.

**Exception — `kind: persona` plugins:** persona manifests are data-only (no
`plugin.sh`, no hooks) and share one page, `docs/wiki/plugins/personas.md`. A new
persona adds its id there instead of a page of its own; `lint-doc-freshness`
checks that every persona id appears in that page, and a per-id persona page is
an orphan it fails.

# Design — GitHub label claim (#1764)

## Goal

Prevent two concurrent zBuild runs on the same issue from overlapping across machines by using a
GitHub label (`zbuild:claimed`) as a soft cross-machine claim. The existing local flock
(`core/state/issue-lock.sh`) remains for intra-machine serialisation; this change adds the
inter-machine layer on top of it, using the same acquire-before-dispatch / release-on-exit shape.

## Context

`core/state/issue-lock.sh` is a filesystem flock: effective on one host, invisible from another.
Issue #1764 asks for a GitHub label that any run can see before it starts. The status-comment
sidecar already shows per-run progress on the issue; the new claim comment is a small companion
comment (machine-readable marker + holder string) that lets a refusing run name the holder.

## Decision

Add `core/claim/claim.sh`:
- `zbuild_claim_acquire <issue> <run_id> <slug>` — check for `zbuild:claimed` on the issue; if
  absent, add it and post a small claim comment (marker `<!-- zbuild-claim run_id=... -->`); if
  present, find the most recent claim comment, extract the holder string into `_ZBUILD_CLAIM_HOLDER`,
  and return 1.
- `zbuild_claim_release <issue> <slug>` — remove the label; PATCH the claim comment to show
  `Status: finished`. Both operations are advisory (failures logged, run never fails).

Wire it into `core/pipeline/runner.sh`:
- Source at the top alongside `core/state/issue-lock.sh`.
- Call `zbuild_claim_acquire` immediately after `zbuild_issue_lock_acquire` succeeds (~line 2452),
  before `_runner_enter_worktree`. On return 1, emit `pipeline.refused.claimed`, print the holder
  string, and return 1 (same shape as the issue-lock refusal).
- Call `zbuild_claim_release` in `_runner_abort_trap` immediately after `zbuild_issue_lock_release`,
  using the same `declare -F` guard.

The "progress comment" referenced by the requirements is this new claim comment, not the
stage-progress sidecar comment (which is unchanged). It is created at claim-time (before first
stage), updated to `finished` on every exit path, and used by a refusing run to identify the holder.

Holder string:
- CI (`GITHUB_ACTIONS=true`): `${GITHUB_SERVER_URL}/${GITHUB_REPOSITORY}/actions/runs/${GITHUB_RUN_ID}`
- Local: `run_id=<id> machine=<hostname>`

The label name is the constant `zbuild:claimed` — no hostname, same in every environment.

Graceful degradation: if `gh` is not available, not authenticated, `NO_GITHUB=true`, or the run has
no issue number, `zbuild_claim_acquire` returns 0 immediately (skip). The local flock still
serialises same-machine runs. Skipping is logged to the run's state dir but never fails the run.

Known limitation: check-then-label is not atomic at GitHub. Two machines racing may both see the
label absent and both succeed. The mechanism prevents honest accidental overlap; a strict distributed
mutex is out of scope (RQMECH-1, RQMECH-2).

```steps
- Create core/claim/claim.sh: zbuild_claim_acquire and zbuild_claim_release, with graceful degradation gates (no issue, NO_GITHUB, gh absent/unauthed) | areas: core/claim/claim.sh
- Wire core/claim/claim.sh into runner.sh: source at top; call zbuild_claim_acquire after zbuild_issue_lock_acquire; call zbuild_claim_release in _runner_abort_trap with declare -F guard | areas: core/pipeline/runner.sh
```

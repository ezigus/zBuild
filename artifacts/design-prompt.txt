### zBuild — Vision

> The North Star for zBuild — it steers how zBuild is built. The README distills it; the wiki references it; every pipeline run is steered by it.

#### Intent
zBuild turns a delivery process into data — templates and plugins — so software is built the same disciplined way every time. We build zBuild the way zBuild builds: a minimal core, with all behavior plugin-delivered and template-composed. A good change is small, aligned to the spec, proven by a test, and wired into the live path — never scaffolding that looks finished but does nothing.

#### Principles
- **Target-agnostic by contract** — zBuild builds *any* repository, not itself; the engine and plugins never assume the target's language, layout, or that zBuild is the target. Target knowledge lives in data — templates, config, per-repo overrides — never in code.
- **Spec wins over drift** — KEEPERS, ARCHITECTURE, and the ADRs are the source of truth; when code disagrees, the code changes, not the spec.
- **Small engine, behavior at the edges** — keep the core tiny; add capability as plugins composed in templates, never by growing the engine.
- **Safety is structural** — all model-bound text passes one redaction chokepoint; state is atomic and resumable; scope is governed at every boundary.
- **Models are data, not code** — selection flows through the router and config tiers; never hardcode a model name.
- **Prove behavior, then wire it** — every change ships a test that fails without it and connects to the live path; green-but-inert is a defect.
- **Fail closed, never silent** — gates block on real problems and say why; bounded cycles and recovery drive work to done.
- **Dogfood every change** — build zBuild with zBuild; if the pipeline can't ship it, fix the pipeline.

### Rules
These are this repository's rules (.zbuild/prompts/rules.md). Work that
breaks one is wrong, whoever wrote it.

- Bash only, and match the file you are in: 4-space indent, LF line endings, a final newline, no trailing whitespace (.editorconfig). Everything must pass `shellcheck` with the repo's .shellcheckrc.
- Never pipe anything into `grep -q`, and never pipe into a bare `head`, in any `.sh` file, test files included. The reader exits early, the writer takes SIGPIPE, and under `set -o pipefail` the line fails for a reason nothing logs. Use a here-string instead: `grep -q PATTERN <<< "$var"`, or run grep on the file directly: `grep -q PATTERN "$file"`. `tests/unit/sigpipe-antipattern-guard-test.sh` fails the suite on any violation; a genuinely safe pipe is annotated `# sigpipe-ok: <reason>`.
- Never name a model (haiku, sonnet, opus, …) in code; model selection goes through core/router and config/models.json.
- A test must be able to fail: assert what is required, never what the code happens to do.
- Never edit anything under `legacy-DoNotUse/`.

#### Facts about this repo
- `ZBUILD_*` environment variables are set by the engine at dispatch (the artifact dir, the stage's input index `ZBUILD_STAGE_INPUTS`, the issue, the run). They are trusted engine inputs, not user or attacker input.
- A stage never builds a path to another stage's output: the engine resolves every input and hands the stage an index (ADR-055 §1). A plugin that derives a path from its state file is a defect.
- Every stage writes a v2 result (`result_contract`, `verdict`, `disposition`, `reason`, detail under `data`) on every exit path, and exits 0 or 1 (ADR-054).
- `[SPEC-n]` / `[#<issue>/SPEC-n]` tags in a test tie an assertion to one issue's acceptance contract. A tag that belongs to another issue must never be changed or removed.

#### Rule ABS — generic enumerated-set / absence-by-omission wisdom

Some closed sets in this repo break by OMISSION rather than by a stale token you
can grep: the breakage is a MISSING (or orphaned) line, not a changed one. When a
change grows, shrinks, or renames such a set, every enumeration of that set is
wrong by omission — yet there is nothing to grep for, because the defect is the
absent entry.

When a change touches a genuinely-closed, exhaustively-enumerated set in this
repo, design MUST include in scope every test or config that enumerates or COUNTS
that set. Because the breakage is an absence, do not trust a hardcoded list of
sites to stay complete — rediscover the sites each time (see "How to find them").

This principle is target-agnostic: it applies to any closed set, and it does not
presume the pipeline stage set is closed (per the ADR-047 tombstone above, it is
not). Use it for sets that are genuinely closed in this repo, declared here per
ADR-032 as this repo's domain-specific enumerations.

#### How to find them

Enumeration/count sites are most often mock-plugin roster blocks (one call per
member) or literal counts of the set. Rediscover them with:

```
grep -rln '_make_plugin\|_make_role_plugin\|_make_verdict_plugin\|mock_plugin_factory' tests/
grep -rln 'stage\.complete\|plugin\.run\.start\|started .*UTC\|finished .*UTC' tests/
```

Every match that enumerates or counts a closed set you are changing belongs in
the design scope block. Re-run the greps each time — new enumeration sites arrive
with new tests, and the defect (a missing line) leaves no token to search for.

#### Rule ABS-W — new plugin directory requires a wiki page

Any change that creates `plugins/<kind>/<id>/manifest.yaml` MUST include
`docs/wiki/plugins/<id>.md` in scope. The `lint-doc-freshness` gate
(`scripts/lib/lint-doc-freshness.sh`) enforces this at test time against the
real repo tree — it fails if the wiki page is absent or lacks a prose opening
paragraph. This is an absence-by-omission gap: there is no old value to grep
for, because the defect is the missing new file.

**Exception — `kind: persona` plugins:** `kind: persona` manifests are
data-only (no `plugin.sh`, no hooks) and share a single index page at
`docs/wiki/plugins/personas.md`. Adding a new persona requires editing
`docs/wiki/plugins/personas.md` to list the new id (one known, stable file)
rather than creating a per-id page. The `lint-doc-freshness` gate enforces
that `personas.md` exists and that every persona id appears as a literal
string in it; per-id pages for personas are not required and will trigger
orphan failures if present.

# Design — issue #1801: per-dispatch stage timeout with orch-sequential retirement

## Architectural decision summary

**Goal**: Every hung `run` hook is killed at its per-stage limit on every dispatch
route; the entire process group (not just the leader) is killed; and the
`orch-sequential` backend is retired.

**Context**: Timeouts existed at the orchestrator layer
(`ZBUILD_ORCH_TIMEOUT`) as a flat per-strategy ceiling, not per dispatch.
`_runner_dispatch_always_run` read `router.timeout_s` (a router budget knob,
not a wall-clock bound for the hook). `orch-sequential` silently discarded any
timeout it was given. `zbuild_pg_kill` existed but was not wired to stage
dispatch.

**Decision**:
1. `plugin_hook_call` (lifecycle.sh) arms a per-dispatch watchdog scoped to the
   "run" hook only. Precedence: `_TPL_STAGE_TIMEOUT_S_<stage>` (template) >
   `ZBUILD_STAGE_TIMEOUT_S` (env) > 5400 s default. The hook subshell runs
   under `set -m` so it forms its own process group; `set +m` inside the hook
   keeps the hook's own children in that same group. **A TERM trap must be
   installed after `_lc_wd_pid` is assigned and before `wait "$_lc_hook_pid"`**
   (between lifecycle.sh lines 516 and 521 in the current build). The trap kills
   both the hook group and the watchdog, then exits with status 143, so that
   when `plugin_hook_call` is externally TERMed (e.g. by `_runner_dispatch_always_run`'s
   outer watchdog) the inner hook group is not orphaned:

   ```bash
   # After:  _lc_wd_pid=$!      (line 516)
   # After:  set +m              (line 517)
   # After:  (( _lc_m_before == 1 )) && set -m  (line 520)
   trap 'zbuild_pg_kill "$_lc_hook_pid" 1 2>/dev/null || true; zbuild_pg_kill "$_lc_wd_pid" 1 2>/dev/null || true; exit 143' TERM
   wait "$_lc_hook_pid" 2>/dev/null; rc=$?
   trap - TERM
   # Before: kill -KILL/zbuild_pg_kill on _lc_hook_pid  (line 525)
   ```

   Without `exit 143` in the trap body, bash resumes execution after the trap
   handler and the outer caller's `wait "$_ar_pid"` stalls indefinitely.

   **Why the SPEC-6b scenario requires this trap**: The test's `build_cleanup` function
   (runner-release-exit-paths-test.sh lines 128-132) spawns a TERM-ignoring child then
   calls bare `wait` — blocking until the child exits (120 s). This turns the cleanup
   hook into a blocking hook, triggering the always_run watchdog after 30 s
   (`stage_timeout_s` in simple.yaml). The watchdog calls `zbuild_pg_kill "$_ar_pid" 10`,
   which sends TERM to pgid `_ar_pid` — the process group of `plugin_hook_call`'s outer
   fork. `_runner_dispatch_always_run` runs `plugin_hook_call` in its own process group
   (outer `set -m` + `&`). The inner hook subshell is a FURTHER nested group
   (`plugin_hook_call`'s own `set -m` + `&`). When TERM arrives at `_ar_pid`'s group,
   it does NOT reach `_lc_hook_pid`'s group (different PGID). Without a TERM trap,
   `plugin_hook_call` exits on TERM before reaching line 525, and the hook child that
   ignores TERM is orphaned and survives.

2. All hand-rolled `kill -KILL/-TERM` sequences for stage dispatch are replaced
   by `zbuild_pg_kill`, specifically:
   - **lifecycle.sh line 525**: `kill -KILL -- -"$_lc_hook_pid" 2>/dev/null || true`
     → `zbuild_pg_kill "$_lc_hook_pid" 1 2>/dev/null || true`
     *(the test grep-scans lifecycle.sh for the literal pattern `kill -KILL -- -"$_lc_hook_pid"` — it fails until that exact string is absent)*
   - **runner.sh lines 2486–2487**: `kill -KILL/-TERM -- -"$_ar_pid"/"$_wd_pid"` → `zbuild_pg_kill`
     *(stage-timeout-always-run-test.sh lines 147-151 AWK-extract `_runner_dispatch_always_run`
     body and check `grep -qE 'kill -(TERM|KILL) -- -"\$_ar_pid"'` — fails until replaced)*
3. `ZBUILD_ORCH_TIMEOUT` is removed from all three strategy files; the per-
   dispatch watchdog in lifecycle.sh is the only ceiling.
4. `plugins/tool/orch-sequential/` is deleted; a `sequential` backend config
   ends the run as `misconfigured`.
5. `simple.yaml` carries `stage_timeout_s` for every stage; `release` = 30 s,
   `persist` = 120 s. `_runner_dispatch_always_run` reads
   `_TPL_STAGE_TIMEOUT_S_<stage>` (not `router.timeout_s`).
6. ADR-054 §9, ADR-017, ADR-011 gain `## Enforced by` sections; both are
   removed from `config/adr-enforcement-baseline.txt`.

**Why the flag-on assertion in runner-job-control-abort-test.sh is superseded**:
The T1 probe records `$-` *inside* `intake_run` (the hook function). lifecycle.sh
forces `set +m` at line 504 before the hook runs, so `$-` inside the hook never
has `m` even when `ZBUILD_RUNNER_JOB_CONTROL=1`. The assertion at test lines 141-147
(`if grep -q 'm' <<< "$_opts_on_1"`) therefore always fails. Replace those lines with

```bash

# stay in the hook's process group). $- inside intake_run therefore never has 'm'.
# Verify structurally that lifecycle.sh arms set -m before the hook spawn.

    assert_pass "flag-on: lifecycle.sh uses set -m before hook spawn [#1801]"
else
```

**Dispatch routes and backends**: The watchdog is installed inside `plugin_hook_call`
in lifecycle.sh, which is above the orchestrator-backend layer. Every dispatch route
— map (strategies/map.sh:plugin_hook_call), fanout (strategies/fanout.sh), sequential
strategy (strategies/sequential.sh), cycle member (runner.sh:2935/3106 via
cycle/parallel orchestrators), parallel-group member (runner.sh:3106), roleless leaf
(runner.sh:3781/3845), and always_run (runner.sh:2477 background dispatch) — reaches
`plugin_hook_call`. All three backends (bash-parallel, ruflo-hive, mock) dispatch
through the same call; the watchdog therefore covers every backend by construction.

**Why SPEC-1 requires an AWK-extracted body check for always_run**: The test for
SPEC-1 (`stage-timeout-dispatch-test.sh`) uses AWK-extracted function bodies to prove
cycle_dispatch_stage and parallel_dispatch_stage call `plugin_hook_call`. The always_run
route (via `_runner_dispatch_always_run`) must be proven the same way. A file-level grep
on runner.sh shows the file contains `plugin_hook_call` but does not prove
`_runner_dispatch_always_run` specifically calls it — any other function in the file
could be the match. The AWK pattern to extract `_runner_dispatch_always_run` is:
`/_runner_dispatch_always_run\(\) \{/{p=1} p{print} p && /^    \}$/{exit}` (it is an
inner function with a 4-space closing brace; this same pattern is used in
`stage-timeout-always-run-test.sh` line 33). The extracted body must contain
`plugin_hook_call` — which it does at runner.sh line 2477.

# Design notes — issue #1801 (fifth refinement)

## Summary of this pass

Single critical fix applied to design-draft.md: `exit 143` → `exit 1` in all
TERM trap references, rationale prose updated.

## What triggered this pass

issue-acceptance findings from the previous iteration:
- `dispatch-rc-guard-test` fails: lifecycle.sh GREW 0→2 legacy-rc returns
  because two TERM trap bodies use `exit 143`, which matches the legacy-rc
  regex `(return|exit)[[:space:]]+(2|…|143)`. The PIN for lifecycle.sh is 0.
- `stage-timeout-precedence-test` isolation section fails: no `sleep 5400`
  captured in the fake-sleep log (secondary effect of broken lifecycle.sh state).

## Root cause

The prior design used `exit 143` in both TERM trap variants (subshell case line
544, main-shell case line 555). The rationale "Without exit 143, bash resumes
execution after the trap handler" was technically wrong: bash terminates when
ANY `exit` appears in a trap body — it does not resume regardless of the status
code. `exit 1` achieves the same unblocking behavior while staying in {0,1}.

1. Decision point 1 pseudocode: `exit 143` → `exit 1`
2. Decision point 1 rationale prose: replaced "exits with status 143" with
   explanation that any explicit exit in a trap body terminates the function,
   and that exit 1 complies with ADR-054 §4 while exit 143 breaks
   dispatch-rc-guard-test.
3. SPEC-2 text: "exits with status 143" → "exits with status 1"
4. supersedes block (runner-release-exit-paths-test.sh): "exits 143" → "exits 1"
5. Added five Findings entries covering the five ia-findings from the last
   issue-acceptance run.

#### performance (score: 8/10)
- [low] plugins/agent/pr-delivery/plugin.sh — ZBUILD_STAGE_INPUTS is parsed with two separate jq subprocess invocations (one for \`.inputs.review_report\`, one for \`.inputs.gate_aggregator_result\`) on the same file; a single \`jq\` call with two outputs or a \`read\` from a single invocation would halve the subprocess cost here, which runs on every non-misconfigured invocation.
- [low] plugins/agent/pr-delivery/plugin.sh — For the \`auto_unless_flagged\` policy when the gate verdict is not \`pass\` and a review_report exists whose \`merge_readiness\` is not \`needs_attention\`, \`merge_readiness\` is extracted from the same file by both the upfront block guard (\`_rr_readiness\` local to that block) and then again by the \`auto_unless_flagged\` branch (\`_auf_readiness\`); the first read's result is not reused, so a redundant jq subprocess is spawned on this code path.
- [low] plugins/agent/pr-delivery/plugin.sh — In \`_pr_delivery_write_result\`, the \`_draft\` normalisation (\`[[ "$_draft" == "true" ]] || _draft="false"\`) executes unconditionally before the \`[[ -z "$_out_dir" ]] && return 1\` guard; the normalisation is wasted work on every call where \`_out_dir\` is empty and the function exits immediately after.

#### red-team (score: 7/10)
- [medium] plugins/agent/pr-delivery/plugin.sh:49 — The \`_pr_delivery_write_result\` helper emits \`draft\` both at the top level of the result envelope and inside \`data\`; the ADR contract reserves the top-level for \`result_contract\`, \`verdict\`, \`disposition\`, \`reason\`, and \`data\`, so the top-level \`draft\` is schema pollution that could confuse strict consumers or schema validators — the old golden (written by pr-open) had \`draft\` only under \`data\`.
- [low] plugins/agent/pr-delivery/plugin.sh:147 — The \`disposition\` string read from the child plugin's result file (\`merge-result.json\` or \`pr-result.json\`) is passed through directly to the parent's v2 result without validating it against ADR-054's vocabulary; a child that writes a non-standard or empty disposition propagates unchecked into the engine's result table.
- [low] plugins/agent/pr-delivery/plugin.sh:133 — \`stage_signal_begin\` is installed at line 133, after the dry-run guard (lines 122–130); a SIGTERM that arrives during the dry-run path's \`atomic_write\` call will not trigger \`_pr_delivery_on_signal\`, leaving no result file — the dry-run path therefore has no signal protection despite \`_PR_DELIVERY_ARTIFACTS_DIR\` being set at line 84.
- [low] plugins/agent/pr-delivery/plugin.sh:244 — When pr-open returns \`verdict=blocked\`, the v2 result unconditionally writes \`reason="review_signal_missing"\` regardless of \`_po_reason\` captured from pr-open's result file; if pr-open ever blocks for a distinguishable reason, the actual reason is silently discarded (only the stage summary retains it via \`${_po_reason:-blocked}\`).
- [low] tests/unit/pr-delivery-v2-result-test.sh:105 — The \`_mk_si\` helper constructs ZBUILD_STAGE_INPUTS JSON via \`printf '%s'\` with file paths; any path that contains JSON-special characters (double quotes, backslashes, newlines) will silently produce invalid JSON and cause the block guard to silently skip input resolution — \`jq -n --arg\` should be used instead.

#### scope (score: 7/10)
- [medium] plugins/agent/pr-delivery/plugin.sh:49 — \`_pr_delivery_write_result\` emits \`draft\` at the top level of the result object (line 49) in addition to inside \`data\` (line 50); ADR-054's v2 envelope schema defines \`{result_contract, verdict, disposition, reason, data}\` — plugin-specific fields belong under \`data\`, and the issue's SPEC-16 only specifies \`data.draft\`, not a top-level \`draft\` key.
- [low] tests/golden/pr-result-artifact.golden:1 — The new golden drops \`data.pr_number\` and \`data.issue\` that pr-open previously populated; the issue specifies \`data.pr_url\` and \`data.draft\` for SPEC-16 but does not ask for removing these downstream-visible fields, and the change does so implicitly because pr-delivery now writes its own result rather than forwarding pr-open's.
- [low] plugins/agent/pr-delivery/manifest.yaml:9 — The description update removes the note "plan.json/design.md are accepted as optional inputs (reserved for future PR-body composition)" — this documented an intentional placeholder not consumed by the one-shot implementation, and its removal is editorial cleanup not asked for by the issue.

#### security (score: 8/10)
- [low] tests/unit/pr-delivery-v2-result-test.sh:168 — The \`_mk_si\` helper and several inline test fixtures construct JSON via \`printf '...%s...' "$path"\`, which produces malformed JSON if any path contains a double-quote, backslash, or newline; \`jq -n --arg key "$val"\` would be safe.
- [low] plugins/agent/pr-delivery/plugin.sh:145 — The disposition value read from \`merge-result.json\` (and analogously from \`pr-result.json\`) is passed through to \`_pr_delivery_write_result\` without validating against the ADR-054 allowed disposition vocabulary; a compromised delegate could inject an arbitrary string into the \`disposition\` field of pr-delivery's own v2 result.
- [low] plugins/agent/pr-delivery/plugin.sh:36 — \`_PR_DELIVERY_ARTIFACTS_DIR\` is initialised to the empty string at source time; if \`_pr_delivery_on_signal\` fires before \`pr_stage_run\` or \`_pr_stage_run_inner\` sets it to a real path, \`_pr_delivery_write_result\` silently returns 1 (the empty-dir guard) and no interrupted result file is written — the contract breach is not surfaced to the caller.

#### sre (score: 7/10)
- [medium] plugins/agent/pr-delivery/plugin.sh:27 — The manifest declares three events (pr.delivery.blocked, pr.delivery.opened, pr.delivery.dry_run) under provides.events — which ADR-001 defines as events the plugin actually emits — but the plugin never emits any of them; the only emit_event call (line 248) fires plugin.result, not pr.delivery.blocked, leaving every monitoring, alerting, or audit trail wired to pr.delivery.* permanently dark.
- [low] plugins/agent/pr-delivery/plugin.sh:133 — stage_signal_begin is installed at line 133, after both the block-guard (lines 106-120) and dry-run path (lines 123-130); a SIGTERM arriving while jq reads the review_report or gate artifact in the block-guard section leaves no pr-result.json on disk — the unguarded window is narrower than before the change (previously the entire function was unprotected) but is non-zero because jq performs file I/O.
- [low] plugins/agent/pr-delivery/plugin.sh:49 — draft appears at the v2 result top level AND nested under data.draft in _pr_delivery_write_result; ADR-054 §4 defines the envelope as {result_contract, verdict, disposition, reason, data} with plugin-specific detail under data, so the top-level draft field is outside the declared schema — confirmed by the updated golden which also carries draft twice.
- [low] tests/golden/pr-result-artifact.golden:1 — The updated golden removes data.pr_number, data.issue, and data.status from pr-result.json (fields previously written by pr-open and now replaced by pr-delivery's own v2 result); any reporting, summary, or downstream tooling that reads data.pr_number from this artifact will silently receive empty — rollback to v1 restores the old fields, so recovery is straightforward.

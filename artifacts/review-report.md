## Review Report

**Merge Readiness:** advisory

19 merge-readiness finding(s) across 6 lens(es) (0 critical, 1 high).

### Lens Findings

#### correctness (score: 7/10)
- [medium] plugins/agent/security-lens/plugin.sh:62 — The \`stub\` field is written as the JSON string \`"false"\` rather than the boolean \`false\` in \`_security_lens_write_result\` (both at the top level and inside \`.data\`); any jq consumer branching on \`.stub\` as a boolean (e.g. \`if .stub then … end\`) will receive a truthy value from the non-empty string, silently inverting the intended semantics — tests using \`jq -r\` do not catch this because \`-r\` renders both \`false\` and \`"false"\` as the output string \`false\`.
- [low] plugins/agent/security-lens/plugin.sh:170 — The \`emit_event\` call on the \`resolve_tier\` failure path hardcodes \`"router_rc=2"\` as a literal key-value string rather than referencing the \`$router_rc\` variable (which is \`0\` at that point in the function); consumers that parse \`router_rc\` as a diagnostic integer will see a sentinel value that conflates tier-resolution failure with a router exit-code-2 failure.
- [low] plugins/agent/security-lens/plugin.sh:170 — The \`emit_event\` on the \`resolve_tier\` fatal path does not include \`result_contract=2\`, while the normal-pass and router-fatal paths both emit that field; downstream consumers asserting that every \`plugin.result\` event from this plugin carries \`result_contract=2\` will see an inconsistent event on the tier-resolution failure branch.
- [low] core/pipeline/runner.sh:1492 — The JSON-validity cross-check at line ~1492 validates \`ZBUILD_STATE_FILE\` even when \`ZBUILD_STATE_DIR\` is also set and will override it in the assignment below; the validated file is never actually used in that scenario, so a corrupt ambient \`ZBUILD_STATE_FILE\` causes a hard error even though it has no effect on the chosen \`state_file\` path — this is intentional per the comment but is a fail-closed behaviour that will surprise callers who set both variables.

#### performance (score: 8/10)
- [low] plugins/agent/security-lens/plugin.sh:52 — \`_security_lens_write_result\` forks \`date -u\` as a subprocess on every invocation; the function is now called on all exit paths (pass, error, interrupt, resolve_tier failure), so error paths that previously paid zero forking cost now pay one extra process fork each — negligible for a once-per-run plugin but a regression relative to the prior code.
- [low] plugins/agent/security-lens/plugin.sh:62 — \`findings_json\` is embedded twice in every result artifact (top-level \`.findings\` and \`.data.findings\`) for backward compatibility; with \`max_findings: 50\` this doubles the JSON payload that \`jq\` must serialize and \`atomic_write\` must flush to disk on every run, increasing output size linearly with finding count.
- [low] plugins/agent/security-lens/plugin.sh:242 — \`printf '%s' "$findings_json" | jq 'length'\` spawns two subprocesses (printf + jq) to compute a count that could be obtained with a single here-string fork (\`jq 'length' <<< "$findings_json"\`); the SIGPIPE risk is absent since jq reads all input, but the extra fork is unnecessary.

#### red-team (score: 6/10)
- [medium] core/pipeline/runner.sh:1489 — Cross-check validates ZBUILD_STATE_FILE against --issue but when both ZBUILD_STATE_FILE and ZBUILD_STATE_DIR are set, ZBUILD_STATE_DIR wins for the actual state source at line ~1695 — the cross-check passes against a file that is never used, leaving the state derived from ZBUILD_STATE_DIR entirely unvalidated and creating a bypass path: an adversary who can set both vars presents a legitimate ZBUILD_STATE_FILE to satisfy the check while pointing ZBUILD_STATE_DIR at an attacker-controlled directory.
- [low] plugins/agent/security-lens/plugin.sh:176 — _sl_interrupted is set to 1 by the TERM/INT trap, but the only place it is checked is on the router_rc==130 branch; if a signal arrives in the window between trap registration and the route_to_model subshell launching, and the subshell subsequently completes with rc=0, the interrupted artifact written by the handler is silently overwritten by the normal pass path, causing an interrupted security review to be reported as verdict=pass.
- [low] plugins/agent/security-lens/plugin.sh:61 — stub field is emitted as JSON string "false" rather than boolean false; downstream consumers that test (.stub == false) in jq or strict JSON parsers that distinguish types will misread the value as truthy, silently treating a real artifact as a stub — tests mask the regression by using jq -r which renders both as the same output string.
- [low] plugins/agent/security-lens/tests/security-lens-test.sh — SPEC-14 assertion (grep -cE '"[^"$]*\.(json|md)"') only matches quoted literals that contain no $ character, so it silently passes for the hardcoded basename in '$ZBUILD_ARTIFACT_DIR/security-findings.json' — the manifest-undeclared basename security-findings.json embedded in the interpolated string is never flagged, and the assertion reports a false clean.

#### scope (score: 7/10)
- [medium] config/event-schema.json — Listed in the design scope; manifest.yaml now declares provides.events with plugin.result and security_lens.failed, but config/event-schema.json was not touched to register these new event types.
- [low] legacy/migrated/security-lens.md — Explicitly listed in the design scope and required by migration discipline (CLAUDE.md: tombstone in legacy/migrated/ when a keeper migrates), but no such file appears in the diff.
- [low] docs/wiki/plugins/security-lens.md — Listed in the design scope alongside other plugin documentation files; the plugin's public contract changed to v2 but the wiki file was not updated.

#### security (score: 7/10)
- [medium] plugins/agent/security-lens/plugin.sh:95 — ZBUILD_ARTIFACT_DIR is used verbatim in \`mkdir -p\` and as the parent of a written artifact with no path validation; an adversary who controls this environment variable (a system boundary per CLAUDE.md) can direct artifact writes to arbitrary filesystem locations via path traversal sequences.
- [low] plugins/agent/security-lens/plugin.sh:79 — _security_lens_interrupt_handler calls _security_lens_write_result which spawns a \`date\` subshell and pipes to atomic_write; running subprocess chains from inside a SIGTERM/SIGINT handler can mask the signal in child processes and prevent the outer pipeline from cleanly propagating the interrupt.
- [low] plugins/agent/security-lens/plugin.sh:178 — _sl_out_ref is set as an unscoped (global) variable before the TERM/INT trap and is never unset after \`trap - TERM INT\`; if the trap fires in a parent context after _security_lens_run_inner returns (e.g., due to a nested call or bash trap inheritance), the stale reference could cause the handler to overwrite an unintended artifact path.

#### sre (score: 6/10)
- [high] plugins/agent/security-lens/plugin.sh — The manifest declares \`security_lens.failed\` as an emitted event, but no \`emit_event "security_lens.failed"\` call appears anywhere in plugin.sh — all error paths emit only \`plugin.result\`, so any monitor or alert wired to \`security_lens.failed\` will never fire.
- [medium] plugins/agent/security-lens/plugin.sh — The rc=130 interrupt path writes a v2 artifact but emits no event to the bus; event-bus consumers watching for \`plugin.result\` or \`security_lens.failed\` cannot distinguish an interrupted review from a review that never ran.
- [medium] plugins/agent/security-lens/plugin.sh:60 — \`stub\` is written as the JSON string \`"false"\` in \`_security_lens_write_result\`, whereas the pre-migration artifact carried the boolean \`false\`; consumers using \`jq -e '.stub'\` or \`.data.stub\` for truthiness checks will silently invert behavior (a string is truthy in jq, a boolean false is falsy).
- [medium] plugins/agent/security-lens/plugin.sh — \`_security_lens_interrupt_handler\` calls \`_security_lens_write_result\` (which spawns \`jq\` and \`atomic_write\`) inside a signal trap; if a second signal arrives during the handler, \`atomic_write\`'s temp-file rename may be abandoned and the artifact left corrupt or absent.
- [low] plugins/agent/security-lens/plugin.sh — \`_sl_out_ref\` and \`_sl_interrupted\` are module-level (non-local) variables; if the shell sources plugin.sh more than once in the same process (e.g. test re-source after SPEC-10 shadow-and-restore), stale values from a prior interrupted run could suppress a required artifact write on the next run.
- [low] core/pipeline/runner.sh:1492 — The cross-check guard now fires even when \`ZBUILD_STATE_DIR\` is explicitly set, meaning a corrupt but ultimately-ignored \`ZBUILD_STATE_FILE\` will abort the pipeline rather than being superseded by the authoritative state dir — the fail-closed behaviour is documented but widens blast radius for operators who set both variables in wrapper scripts.

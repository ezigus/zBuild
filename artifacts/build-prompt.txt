### zBuild — Vision

> The North Star for zBuild — it steers how zBuild is built. The README distills it; the wiki references it; every pipeline run is steered by it.

#### Intent
zBuild turns a delivery process into data — templates and plugins — so software is built the same disciplined way every time. We build zBuild the way zBuild builds: a minimal core, with all behavior plugin-delivered and template-composed. A good change is small, aligned to the spec, proven by a test, and wired into the live path — never scaffolding that looks finished but does nothing.

#### Principles
- **Target-agnostic by contract** — zBuild builds *any* repository, not itself; the engine and plugins never assume the target's language, layout, or that zBuild is the target. Target knowledge lives in data — templates, config, per-repo overrides — never in code.
- **Spec wins over drift** — KEEPERS, ARCHITECTURE, and the ADRs are the source of truth; when code disagrees, the code changes, not the spec.
- **Small engine, behavior at the edges** — keep the core tiny; add capability as plugins composed in templates, never by growing the engine.
- **Safety is structural** — all model-bound text passes one redaction chokepoint; state is atomic and resumable; scope is governed at every boundary.
- **Models are data, not code** — selection flows through the router and config tiers; never hardcode a model name.
- **Prove behavior, then wire it** — every change ships a test that fails without it and connects to the live path; green-but-inert is a defect.
- **Fail closed, never silent** — gates block on real problems and say why; bounded cycles and recovery drive work to done.
- **Dogfood every change** — build zBuild with zBuild; if the pipeline can't ship it, fix the pipeline.

### Rules
These are this repository's rules, from its .zbuild/rules.md. Work that
breaks one is wrong, whoever wrote it.

#### Rules
- If the code drifts from the spec, the spec wins: docs/KEEPERS.md, docs/ARCHITECTURE.md and docs/adr/. PRs cite the relevant ADR or KEEPERS section in the description. Every issue cites the ADR and section it implements; if no ADR covers the change, the issue first creates one or amends an existing one. ADRs must not contradict each other: a later decision amends the earlier ADR in the same PR.
- Every ADR statement has a test, named in the ADR's Enforced by section. A rule that lives only in an ADR's prose is a missing test: when a run passes something wrong, look first for the ADR statement nothing enforces, and write that test. Every live ADR has an `## Enforced by` section naming, per statement (§), the test or lint that enforces it; a new or changed statement ships with its test in the same PR. `scripts/lib/lint-adr-enforced-by.sh` (in `npm run lint`) fails a live ADR without the section, or one naming a file that does not exist. ADRs written before this rule are listed in `config/adr-enforcement-baseline.txt`, which only shrinks.
- Write the test first. Before editing any file under `core/`, `plugins/`, or `scripts/`, write (or amend) the test that expresses the required behavior, run it, and confirm it FAILS — and fails for the reason you intend, not on a typo or a missing fixture. Only then write the implementation; then re-run and watch it go green. A test written after the implementation asserts what the code does, not what was required, so it stays green while the code is wrong: order the work so the test cannot be shaped by the implementation. Reverting the implementation afterwards to check the test goes red is NOT test-first — it produces the same two files and a weaker test, because the assertion was still authored while looking at the code; use it to verify an inherited test, never as a substitute for the ordering. State the red step in the PR body: the assertion, and how it failed before the fix.
- Data another part of the engine writes is checked against its writer. When a change reads something another part of the code writes — pipeline-state.json, another stage's result, an event — open the writer and use the names it really writes, when it writes them. A test makes such data with the writer's own code (e.g. `zb_engine_loop_state` for loop state; `lint-test-engine-state.sh` refuses a hand-written `cycle_iterations`), never by hand: hand-made data holds whatever its author assumed.
- Tests are deterministic (ADR-012). A remote service is faked at the project's own wrapper around it, never the project's own code: `gh`, `claude`, `curl` and the network are faked, at the innermost wrapper listed in `config/test-fake-wrappers.txt`; signals sent to the engine stay real. Never wait on a clock in a test: no sleep before a check or a signal — wait for a marker the process writes, with a timeout. `scripts/lib/lint-test-determinism.sh` enforces it.
- Keep files under 500 lines.
- Process and exec budgets only go down: a change to work zBuild already does never raises what it costs, and a change that lowers it lowers the budget (`tests/e2e/fork-budget-test.sh`, ADR-065).
- Bash only, and match the file you are in: 4-space indent, LF line endings, a final newline, no trailing whitespace (.editorconfig). Everything must pass `shellcheck` with the repo's .shellcheckrc.
- Never pipe anything into `grep -q`, and never pipe into a bare `head`, in any `.sh` file, test files included. The reader exits early, the writer takes SIGPIPE, and under `set -euo pipefail` the surrounding function dies for a reason nothing logs. Use a here-string instead: `grep -q PATTERN <<< "$var"`, or run grep on the file directly: `grep -q PATTERN "$file"`, or capture in full and trim in bash. `tests/unit/sigpipe-antipattern-guard-test.sh` fails the suite on any violation; a genuinely safe pipe is annotated `# sigpipe-ok: <reason>`.
- Never name a model (haiku, sonnet, opus, …) in code: all model selection goes through core/router reading config/models.json. Tier ordinals (T0–T4) are stable; model names change (ADR-003).
- A test must be able to fail: assert what is required, never what the code happens to do.
- Never edit anything under `legacy-DoNotUse/`.

#### Facts about this repo
- `ZBUILD_*` environment variables are set by the engine at dispatch (the artifact dir, the stage's input index `ZBUILD_STAGE_INPUTS`, the issue, the run). They are trusted engine inputs, not user or attacker input.
- A stage never names another stage's output — not its output name, not its file. The engine hands every stage every earlier stage's latest output, and a stage finds what it needs by what it contains (scripts/lib/earlier-output.sh; ADR-055 §1). A plugin that names another stage's output is a defect.
- Every stage writes a v2 result (`result_contract`, `verdict`, `disposition`, `reason`, detail under `data`) on every exit path, and exits 0 or 1 (ADR-054).
- `[SPEC-n]` / `[#<issue>/SPEC-n]` tags in a test tie an assertion to one issue's acceptance contract. A tag that belongs to another issue must never be changed or removed.

# Design: Concurrent-claim race detection (issue #2534)

## Decision

GitHub's label API has no check-and-set: two runs can both read "no claim" and both add
`zbuild:claimed`, each getting a success reply. After adding the label (gh backend only),
the coordinator posts a concurrent claim note — `"concurrent claim by \`<holder>\`"` —
then re-reads the GitHub issue itself (its labels or state), then reads back all trusted
concurrent claim notes. The note is the synchronous holder record (RQTIE-3 path 1). The
run whose note is first by GitHub's `created_at` (then `id` on a tie) is the winner; it
returns `{"acquired": true}`. Every other run marks its note "not started — concurrent
claim: `<winner>` was first" and returns
`{"acquired": false, "holder": "<winner>", "race_lost": true}`. The engine receives
`race_lost: true` and refuses immediately, skipping the stale-takeover path that would
otherwise trigger for any cross-machine refusal. ADR-005 gains §5 to document all of this.

Why the stale-takeover path cannot set `_ZBUILD_CLAIM_ACQUIRED` for a race-lost response:
in `zbuild_claim_acquire`, the new `race_lost: true` branch (DSRACE-5) returns 1 before
the code reaches `_zbuild_claim_takeover`, so the takeover's `_ZBUILD_CLAIM_ACQUIRED="$issue"`
assignment is never reached. DSRACE-4 is [code] because that guarantee requires DSRACE-5 to
be in place; without it, the existing takeover path can and does set `_ZBUILD_CLAIM_ACQUIRED`.

Reviewed alternatives: GitHub's `labeled` events are not usable as the tie-break — GitHub
does not create a second `labeled` event when the label is already there, so the events
give no information about concurrent adders. The local-fs test backend is unaffected; its
`flock`-serialised add already returns rc 2 for a duplicate add.

Outside assumptions:
- `rsc_gh` and `jq` are available in the coordinator (already used throughout `plugin.sh`)
- GitHub's comment `created_at` and `id` are ordered and stable (standard API guarantee)
- The concurrent claim note format (`"concurrent claim by \`"`) is distinct from takeover
  notes (`"took over a stale claim from \`"`) — no interference

What each SPEC requires:
- [DSRACE-1] After successfully adding the zbuild:claimed label (gh backend), the claim posts a concurrent claim note with the run's holder, then reads back all trusted concurrent claim notes to detect concurrent claimants — Given: the zbuild:claimed label was just successfully added via the gh backend — When: the claim posts a "concurrent claim by `<holder>`" note and reads back all trusted concurrent claim notes since the note's own created_at minus the detection window — Then: the note is posted synchronously before the read-back — And: all concurrent claim notes from the current label epoch are returned
- [DSRACE-2] Only the run whose concurrent claim note is first (by created_at, then id) returns {"acquired": true}; all others return {"acquired": false} — Given: two or more concurrent claim notes exist for the same issue within the detection window — When: each run compares the notes and identifies the first — Then: the run whose note has the earliest created_at returns {"acquired": true} — And: all other runs return {"acquired": false, "holder": "<winner_holder>", "race_lost": true}
- [DSRACE-3] The losing run updates its concurrent claim note body to "not started" — Given: the run's concurrent claim note is not the first by created_at (or id) — When: the run determines it has lost the race — Then: the run PATCHes its note body to "not started — concurrent claim: `<winner>` was first"
- [DSRACE-4] When zbuild_claim_acquire receives {"acquired": false, "race_lost": true} from the coordinator, _ZBUILD_CLAIM_ACQUIRED is not set and zbuild_claim_release does not remove the zbuild:claimed label — Given: claim_coordinator_claim returns {"acquired": false, "race_lost": true} — When: zbuild_claim_acquire processes the response — Then: _ZBUILD_CLAIM_ACQUIRED is not set — And: zbuild_claim_release does not remove the zbuild:claimed label
- [DSRACE-5] A coordinator response with race_lost: true causes zbuild_claim_acquire to refuse immediately without entering the stale-takeover path, printing a message that names the concurrent winner — Given: claim_coordinator_claim returns {"acquired": false, "holder": "<winner>", "race_lost": true} — When: zbuild_claim_acquire processes the response — Then: the stale-takeover hook is not called — And: stderr names the concurrent winner as the first claimant
- [DSRACE-6] ADR-005 §5 tells a reader: after adding the label (gh backend), a note is posted as the holder record, the first note by created_at then id wins, the loser marks its note "not started", and race_lost: true in the refused response skips the stale-takeover path
- [DSRACE-7] After posting the concurrent claim note (the synchronous holder record, gh backend), the claim reads back the GitHub issue's current state before proceeding with arbitration — Given: the zbuild:claimed label was added and the concurrent claim note was posted synchronously — When: the claim reads the GitHub issue's current labels or state — Then: fresh issue data is obtained from GitHub after the synchronous holder record was written

### The files you may change
You may change any file outside the test folders (tests/*, plugins/*/*/tests/*), and none inside them. Every file in the test folders — a test, a fixture, a test helper — belongs to the stage that writes the tests: a change you make there is put back.

### Rules
- Do not run `git commit` — the pipeline owns commit semantics.
- NEVER run a command that mutates git branch state or the working tree —
  no `git checkout -b`/`switch`/`commit`/`push`/`tag`/`reset`. You are running
  INSIDE the pipeline's own checkout; switching or creating a branch hijacks the
  run. The pipeline owns the branch.
- If you must exercise a command you are building (or any command that could
  publish, tag, push, or otherwise mutate state), run it in `--dry-run` mode.
  Do everything you can to verify behavior without side effects.
- Keep changes minimal and aligned with the design: change what the task needs.
- Clean up scratch siblings of the files you edit (`*.bak`, `*.orig`,
  `*.rej`, `*.head`, `*.tmp`, `*~`). `sed -i.bak` and
  `git show HEAD:f > f.head` both leave one behind — prefer `sed -i` with no
  suffix, and delete any comparison scratch before you finish. A new scratch
  file is removed for you; every other file you leave is part of your change.

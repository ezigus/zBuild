## Review Report

**Merge Readiness:** advisory

17 merge-readiness finding(s) across 6 lens(es) (0 critical, 0 high).

### Lens Findings

#### correctness (score: 7/10)
- [medium] plugins/tool/test/plugin.sh:879 — The hardcoded fallback JSON string (jq-failure path) omits \`exit_code\`, \`test_output\`, and \`run_mode\` at the top level, so any consumer relying on the new top-level fields (asserted by SPEC-3/4/7) receives null from the fallback path, making the fallback output inconsistent with the v2 contract the primary write path now satisfies.
- [low] plugins/tool/test/tests/test-test.sh:660 — SPEC-8 joins two unrelated assertions with a pipe-delimiter (\`"interrupted|true"\` vs \`"${_spec8_term}|${_spec8_has_to}"\`): if only one sub-check fails the error message cannot identify which, and the \`has("test_output")\` half duplicates SPEC-1's check on the same artifact without adding coverage.
- [low] plugins/tool/test/tests/test-test.sh:629 — SPEC-3 and SPEC-4 each issue two \`assert_eq\` calls under the same label prefix (e.g. both \`[SPEC-3]\` lines), so when a runner reports failures by label, both assertions are indistinguishable and the specific failing sub-check (exit_code vs disposition) is hidden.

#### performance (score: 9/10)
- [low] plugins/tool/test/tests/test-test.sh:651 — SPEC-3, SPEC-4, SPEC-5, SPEC-6, and SPEC-8 each spawn a second jq subprocess on the same already-read JSON file where a single jq call could extract all needed fields in one pass, adding ~5 extra process forks to the test run; negligible in practice but avoidable.

#### red-team (score: 7/10)
- [medium] plugins/tool/test/tests/test-test.sh:609 — All result_contract=2 schema-version checks are removed from SPEC-1 through SPEC-8; a v1 result that happens to include the newly checked top-level fields (test_output, run_mode, exit_code) will pass every SPEC assertion without ever proving the schema version contract is enforced.
- [medium] plugins/tool/test/tests/test-test.sh:656 — SPEC-7 reversal: the prior assertion explicitly required exit_code to be absent at top level (enforcing data encapsulation under data.{}); the replacement now requires it at top level, silently widening the information surface exposed to downstream consumers without a guard that the data.exit_code path is still present on error paths.
- [low] plugins/tool/test/tests/test-test.sh:667 — SPEC-8 combines an unrelated field-presence check (test_output at top level) with the signal-death mapping assertion using pipe-delimited string concatenation; a failure in either half produces an opaque mismatch string that cannot distinguish which invariant broke, masking regressions.
- [low] plugins/tool/test/tests/test-test.sh:636 — SPEC-3 and SPEC-4 each emit two assert_eq calls sharing the same tag string ([SPEC-3], [SPEC-4]); test harnesses that match on tag to count or report failures will attribute both failures to the same spec, obscuring whether the exit_code or disposition invariant broke.
- [low] tests/unit/test-plugin-result-write-fallback-test.sh:142 — SPEC-11 in the fallback writer test drops the result_contract=2 version check and replaces it with run_mode=full; run_mode can equal 'full' on a v1 or otherwise malformed result, so this no longer guards the v2 calling convention it claims to verify.

#### scope (score: 6/10)
- [medium] /home/runner/work/_temp/zbuild-state/scope-manifest.md — Scope manifest could not be read (permission denied), so out-of-scope edits and in-scope-but-untouched files cannot be fully enumerated against the declared plan.
- [medium] plugins/tool/test/plugin.sh:850 — Adding exit_code at the top-level result (alongside data.exit_code) is an implementation contract change that may extend beyond the original scope; prior SPEC-7 explicitly asserted exit_code must NOT appear at top level, and the plan may not have included promoting it there.
- [medium] plugins/tool/test/tests/test-test.sh:665 — SPEC-7 was semantically inverted: the original assertion tested that exit_code is absent at top level (data-encapsulation); the replacement asserts it is present at top level — a contract reversal that may be an unplanned scope expansion rather than a refinement.
- [low] plugins/tool/test/tests/test-test.sh:609 — SPEC-1 through SPEC-8 were completely re-authored to assert different fields (test_output, run_mode, exit_code at top level) rather than the original contract fields (result_contract, disposition, data encapsulation); if the plan described specific SPEC assertions, the replacement assertions may drift from that declared scope.

#### security (score: 9/10)
- [low] plugins/tool/test/tests/test-test.sh:663 — The pipe-concatenated assertion \`"interrupted|true"\` vs \`"${_spec8_term}|${_spec8_has_to}"\` could silently pass if either variable contains a literal pipe character from adversarial plugin output, but since both values come from controlled internal functions (\`_test_disposition_from_rc\` and \`jq\`), practical risk is negligible.

#### sre (score: 6/10)
- [medium] plugins/tool/test/plugin.sh:851 — exit_code is now emitted at both the top level and inside data.exit_code with no test asserting they are equal; if a code path updates one but not the other, downstream consumers reading different paths will see divergent state silently.
- [medium] plugins/tool/test/tests/test-test.sh:613 — SPEC-1 no longer asserts result_contract=2, so a regression that emits schema_version:1 or drops the contract marker entirely will go undetected by this suite, removing the canary for schema-version-aware consumers.
- [low] plugins/tool/test/tests/test-test.sh:657 — SPEC-8 concatenates two unrelated checks into a single assert_eq string ("interrupted|true"); a failure produces an opaque diff and makes it impossible to identify which sub-check failed without re-running manually.
- [low] plugins/tool/test/tests/test-test.sh:621 — SPEC-2 no longer validates the disposition field on any path; if disposition starts emitting a wrong value (e.g. null or an unexpected string), no SPEC assertion will catch it until SPEC-3/4/5 fire on a different code path.

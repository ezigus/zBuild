### zBuild — Vision

> The North Star for zBuild — it steers how zBuild is built. The README distills it; the wiki references it; every pipeline run is steered by it.

#### Intent
zBuild turns a delivery process into data — templates and plugins — so software is built the same disciplined way every time. We build zBuild the way zBuild builds: a minimal core, with all behavior plugin-delivered and template-composed. A good change is small, aligned to the spec, proven by a test, and wired into the live path — never scaffolding that looks finished but does nothing.

#### Principles
- **Target-agnostic by contract** — zBuild builds *any* repository, not itself; the engine and plugins never assume the target's language, layout, or that zBuild is the target. Target knowledge lives in data — templates, config, per-repo overrides — never in code.
- **Spec wins over drift** — KEEPERS, ARCHITECTURE, and the ADRs are the source of truth; when code disagrees, the code changes, not the spec.
- **Small engine, behavior at the edges** — keep the core tiny; add capability as plugins composed in templates, never by growing the engine.
- **Safety is structural** — all model-bound text passes one redaction chokepoint; state is atomic and resumable; scope is governed at every boundary.
- **Models are data, not code** — selection flows through the router and config tiers; never hardcode a model name.
- **Prove behavior, then wire it** — every change ships a test that fails without it and connects to the live path; green-but-inert is a defect.
- **Fail closed, never silent** — gates block on real problems and say why; bounded cycles and recovery drive work to done.
- **Dogfood every change** — build zBuild with zBuild; if the pipeline can't ship it, fix the pipeline.

### Rules
These are this repository's rules (.zbuild/prompts/rules.md). Work that
breaks one is wrong, whoever wrote it.

- Bash only, and match the file you are in: 4-space indent, LF line endings, a final newline, no trailing whitespace (.editorconfig). Everything must pass `shellcheck` with the repo's .shellcheckrc.
- Never pipe anything into `grep -q`, and never pipe into a bare `head`, in any `.sh` file, test files included. The reader exits early, the writer takes SIGPIPE, and under `set -o pipefail` the line fails for a reason nothing logs. Use a here-string instead: `grep -q PATTERN <<< "$var"`, or run grep on the file directly: `grep -q PATTERN "$file"`. `tests/unit/sigpipe-antipattern-guard-test.sh` fails the suite on any violation; a genuinely safe pipe is annotated `# sigpipe-ok: <reason>`.
- Never name a model (haiku, sonnet, opus, …) in code; model selection goes through core/router and config/models.json.
- A test must be able to fail: assert what is required, never what the code happens to do.
- Never edit anything under `legacy-DoNotUse/`.

#### Facts about this repo
- `ZBUILD_*` environment variables are set by the engine at dispatch (the artifact dir, the stage's input index `ZBUILD_STAGE_INPUTS`, the issue, the run). They are trusted engine inputs, not user or attacker input.
- A stage never names another stage's output — not its output name, not its file. The engine hands every stage every earlier stage's latest output, and a stage finds what it needs by what it contains (scripts/lib/earlier-output.sh; ADR-055 §1). A plugin that names another stage's output is a defect.
- Every stage writes a v2 result (`result_contract`, `verdict`, `disposition`, `reason`, detail under `data`) on every exit path, and exits 0 or 1 (ADR-054).
- `[SPEC-n]` / `[#<issue>/SPEC-n]` tags in a test tie an assertion to one issue's acceptance contract. A tag that belongs to another issue must never be changed or removed.

### DESIGN DECISIONS (from the design stage — honor these directives; they refine the plan)
# Design — Issue #1944: run-level wall-clock limit

## Architectural decision

**Goal.** Enforce a per-run wall-clock ceiling so no pipeline run is unbounded.

**Context.** Only per-stage `router.timeout_s` knobs existed. A deadlock
between stages or a slow stage without a per-stage limit can run indefinitely.
CI platforms carry their own job ceilings; the engine must enforce its own
without reading platform variables (R-8).

**Decision.**

1. **Limit resolution** (`_runner_resolve_run_limit_s` in
   `scripts/lib/stage-limits.sh`): template top-level `max_run_s:` key
   (via `template_max_run_s()` in `core/pipeline/template.sh`) >
   `ZBUILD_MAX_RUN_S` env > 20700 s default. A non-integer or non-positive
   value in either source is misconfigured; the runner exits 1 before any
   stage runs.

2. **Watchdog.** A background subshell is armed in `main()` after the traps
   are installed. It sleeps for the resolved limit, writes `timed_out` to the
   abort sentinel (first-wins semantics), then sends SIGTERM to the runner's
   process group. After a 10-second grace it sends SIGKILL to the runner's
   child processes (not the runner itself, so the runner's deferred SIGTERM
   trap can fire and exit with rc=1, which lets the EXIT trap dispatch
   `always_run` stages). The watchdog ignores SIGTERM so it survives its own
   PG-wide TERM and can escalate to KILL. Raw kill (not `zbuild_pg_kill`)
   because the watchdog is in the runner's own process group, which
   `zbuild_pg_kill` refuses.

3. **Watchdog subshell must close the inherited pipe-bearing fd from inside its
   body.** When the runner is invoked inside `$(bash "$RUNNER" ... 2>&1)` (as
   existing tests do), bash creates a pipe; both stdout and stderr of the runner
   point to its write end. Before the watchdog is armed, `main()` runs
   `exec {_RUNNER_ERR_FD}>&2` (line 2745) to save a copy of stderr on a
   high-numbered fd (`_RUNNER_ERR_FD` ≥ 10). The watchdog subshell inherits
   this fd. The `>/dev/null 2>&1 &` redirect closes fds 1 and 2 in the
   watchdog, but `_RUNNER_ERR_FD` is NOT covered. When the watchdog is
   SIGKILL'd by the EXIT trap, its `sleep "$_wdg_lim"` child is ORPHANED — it
   still holds `_RUNNER_ERR_FD` (the pipe write end). The `$(...)` waits for
   ALL file-description holders; the orphaned sleep holds one indefinitely,
   causing a 480 s test timeout.
   **Fix:** add `exec {_RUNNER_ERR_FD}>&- || true` as the SECOND line inside
   the watchdog body (after `trap '' TERM`). Close it in the body — NOT as a
   redirect on the `( ... ) &` boundary. The launch line stays `>/dev/null 2>&1 &`.
   Closing at the boundary with `    ) >/dev/null 2>&1 {_RUNNER_ERR_FD}>&- &`
   instead caused a regression in `runner-release-exit-paths-test.sh` SPEC-5
   (see Finding 18): `release` was no longer dispatched on the hard-kill exit
   path. Closing inside the body avoids the issue entirely while achieving the
   same effect: the `sleep` child inherits fds 1=/dev/null, 2=/dev/null, and
   fd{N}=closed (already closed before `sleep` was forked), so no orphaned
   process can hold the pipe write end.

4. **EXIT trap must guard against repeat signals with `trap ':' INT TERM` as
   its absolute first executable line.** The tests drive the runner via
   `timeout 120 bash "$RUNNER" ...` and send `kill -TERM -$RUNNER_PID` to the
   process group. GNU `timeout`, on receiving SIGTERM, forwards SIGTERM to its
   child's process group (same PG) before exiting. The runner therefore
   receives TWO SIGTERMs. The first fires `_runner_signal_trap TERM` →
   `exit 1` → the EXIT trap (`_runner_abort_trap`) starts. The second SIGTERM
   can arrive at any point before `trap ':' INT TERM` is installed. Bash fires
   `_runner_signal_trap TERM` again, which calls `exit 1`. Calling `exit`
   from within an EXIT trap causes bash to abort the trap immediately —
   `_runner_dispatch_always_run` is never reached.
   **Fix:** `trap ':' INT TERM` must be the ABSOLUTE FIRST EXECUTABLE LINE of
   `_runner_abort_trap` — before `_runner_restore_stderr` and before anything
   else. Any code that precedes the guard creates a race window, regardless of
   whether it calls `wait`. `_runner_restore_stderr` follows immediately after
   (still before any wait-bearing or dispatching code). The guard is restored
   to real handlers after the kill/wait block so `_runner_dispatch_always_run`
   can still handle signals. Mirrors the pattern used inside
   `_runner_dispatch_always_run` (line 2516).
   **Current worktree defect (Finding 21):** `_runner_restore_stderr` is at
   line 2532 and `trap ':' INT TERM` is at line 2543. The race window between
   them causes `runner-release-exit-paths-test.sh` SPEC-5 to fail — the
   second SIGTERM aborts the EXIT trap before `_runner_dispatch_always_run`
   runs, leaving the release marker empty.

5. **runner-signal-rearm-test.sh SPEC-5 regression.** The Bug B fix (Decision
   4) defines `_runner_abort_trap()` inside `main()`. This nested function
   contains `trap ':' INT TERM` — a guard line that ends with `TERM`. The
   SPEC-5 awk pattern `/trap .* TERM$/` finds this line as the FIRST
   `trap...TERM` inside `main()` (the nested function definition precedes the
   startup install at line 2751). The subsequent `grep -oE "trap '[^']+' TERM"`
   does not match `trap ':' INT TERM` (two-signal form), so `_startup_term`
   comes up empty (`<startup-not-found>`), while `_rearm_term` from
   `_runner_rearm_traps` is `trap '_runner_signal_trap TERM' TERM`. Test fails.
   **Fix:** narrow the awk pattern in SPEC-5 to match only single-handler TERM
   installs: replace `/trap .* TERM$/` with `/trap '.*' TERM$/` (requires a
   single-quoted handler before `TERM`). This skips `trap ':' INT TERM` (whose
   arg ends with `INT TERM`, not `' TERM'`) and correctly finds the startup
   `trap '_runner_signal_trap TERM' TERM` install.

6. **New abort word and pipeline status.** `timed_out` is the seventh abort
   word (ADR-025) and a new pipeline status (ADR-006, ADR-015). A
   `timed_out` state is `manual_resume_only` (resume.sh). A resumed run
   receives a fresh watchdog armed from its own wall-clock start.

7. **Always-run stages (release AND persist) still execute** via
   `_runner_dispatch_always_run` in the abort trap, which fires before the
   timed_out path writes the final state. Both role types are in the
   `timeout-with-release` test template's `always_run` list and both are
   asserted in P4 of run-timed-out-test.sh.

### Root cause analysis — SPEC-5:

The test sends `kill -TERM -$RUNNER_PID` to the process group. In SPEC-5, the runner
is wrapped in `timeout 120 bash runner.sh`. When `timeout 120` receives SIGTERM:
1. It forwards SIGTERM to its child (runner bash)
2. It exits

So runner bash gets TWO SIGTERMs:
- First: from the process-group kill directly
- Second: from `timeout` forwarding

**The double-SIGTERM problem in detail:**

Bash's signal model: pending signals are checked at command boundaries
(after each command completes). In `_runner_abort_trap`:

```
_runner_abort_trap() {
    _runner_restore_stderr    # command 1 (first stmt - required by B3)
    trap ':' INT TERM         # command 2 (guard)
```

Sequence:
1. First SIGTERM → `_runner_signal_trap TERM` → `exit 1` → EXIT trap fires
2. `_runner_abort_trap` starts executing
3. `_runner_restore_stderr` executes (very fast: `exec 2>&N`)
4. `_runner_restore_stderr` RETURNS → bash checks pending signals
5. Second SIGTERM is pending → fires `_runner_signal_trap TERM` → `exit 1` from EXIT trap → ABORT
6. `trap ':' INT TERM` NEVER EXECUTES
7. `_runner_dispatch_always_run` NEVER EXECUTES → marker is empty

This is consistent (not a race) because `timeout` forwards SIGTERM very quickly,
making the second SIGTERM pending before or during the first handler execution.
When bash unblocks SIGTERM after the EXIT trap starts, the second SIGTERM fires
at the first command boundary (after `_runner_restore_stderr` returns).

**Why SPEC-1 through SPEC-4 don't fail:**
- SPEC-1, 2, 3: no SIGTERM involved (success/nonzero/SIGINT paths)
- SPEC-4: uses `setsid bash -c '... exec bash ...'` (new session, no `timeout` wrapper)
  → only ONE SIGTERM reaches the runner

**Why runner-abort-banner-stderr-test.sh B3 constrains the fix:**
B3 checks that `_runner_restore_stderr` is the FIRST non-blank, non-comment
statement in `_runner_abort_trap`. So I cannot move `trap ':' INT TERM` BEFORE
`_runner_restore_stderr` at the `_runner_abort_trap` level.

**THE FIX:**
Move `trap ':' INT TERM` INSIDE `_runner_restore_stderr` as its FIRST statement:

```bash
_runner_restore_stderr() {
    trap ':' INT TERM   # guard: called only from _runner_abort_trap (EXIT trap)
    [[ -n "${_RUNNER_ERR_FD:-}" ]] && exec 2>&"$_RUNNER_ERR_FD"
    return 0
}
```

This works because:
- Bash checks pending signals BETWEEN commands, not DURING a function call's entry
- When `_runner_abort_trap` calls `_runner_restore_stderr`, bash enters the function
  body and executes `trap ':' INT TERM` as the first instruction INSIDE
  `_runner_restore_stderr`
- When `_runner_restore_stderr` RETURNS back to `_runner_abort_trap`, the guard
  is already active
- If the second SIGTERM fires at that return boundary, it's handled as a noop

B3 passes: first non-blank, non-comment statement in `_runner_abort_trap` is still
`_runner_restore_stderr`. The trap setting is INSIDE that function.

## Review Report

**Merge Readiness:** advisory

22 merge-readiness finding(s) across 6 lens(es) (0 critical, 0 high).

### Lens Findings

#### correctness (score: 7/10)
- [medium] plugins/agent/validate/tests/validate-test.sh — SPEC-25's hook-count assertion uses grep pattern '^[[:space:]]+[a-z_]+:' which matches every indented YAML key, not just top-level hook names — if the manifest's 'run:' entry uses block-mapping syntax (e.g., 'run:\n  command: ...'), 'command:' would also match and the count would exceed 1, falsely failing the assertion.
- [low] plugins/agent/validate/plugin.sh — In validate_agent_run, the v2 result write is guarded by 'if [[ -n "${ZBUILD_ARTIFACT_DIR:-}" ]]', so when ZBUILD_ARTIFACT_DIR is unset the missing-state-file exit path produces no artifact — SPEC-14 is scoped to _validate_agent_run_inner and does not cover this path, leaving the 'every exit path writes a result' invariant untested for this code path.
- [low] plugins/agent/validate/plugin.sh — The condition 'if [[ -n "$_si_path" && -f "$_si_path" ]]' contains a vacuous check: _si_path is assigned via '${ZBUILD_STAGE_INPUTS:-$(dirname "$state_file")/stage-inputs.json}' and is therefore never empty, making the '-n' guard always true and potentially misleading about what controls input-file resolution.
- [low] plugins/agent/validate/tests/validate-test.sh — SPEC-24's event-count check 'grep -c 'validate\.' <<< "$_s24_events"' counts string occurrences of 'validate.' in list-item lines, but if any event name appears more than once on its line (e.g., in a comment or description field), the count would overstate the number of declared events.

#### performance (score: 9/10)
- [low] plugins/agent/validate/tests/validate-test.sh:215 — _v2_keys_ok spawns four separate jq subprocesses on the same file to extract four fields; a single jq call with multiple outputs would halve the subprocess count, though this is test-only code so impact is limited to suite wall-clock time.

#### red-team (score: 6/10)
- [medium] plugins/agent/validate/plugin.sh:75 — The \`deploy_result_in\` path is extracted raw from attacker-controlled JSON via \`jq -r '.inputs.deploy_result // empty'\` and then used directly in a file-existence guard (\`[[ ! -f "$deploy_result_in" ]]\`) with no boundary check; an adversary who controls \`ZBUILD_STAGE_INPUTS\` content can supply a path to any world-readable file (e.g. \`/etc/passwd\`) and cause the guard to pass, making the plugin proceed as if a valid deploy result was provided.
- [medium] plugins/agent/validate/plugin.sh:88 — \`ZBUILD_DRY_RUN=1\` is trusted as an environment variable with no integrity check, allowing any caller that can set the variable to bypass all health-probe execution and receive a \`result_contract:2, verdict:healthy, disposition:complete\` result — a full authentication bypass of the validation stage.
- [low] plugins/agent/validate/plugin.sh:67 — \`ZBUILD_ARTIFACT_DIR\` is accepted from the environment and passed directly to \`mkdir -p\` and \`atomic_write\` without any path-boundary validation, so a caller that controls this variable can direct result artifacts to an arbitrary filesystem location (directory traversal / write escalation).
- [low] plugins/agent/validate/plugin.sh:120 — \`hc_snippet\` — the first 500 bytes of unchecked health-probe stdout — is interpolated into the stage-summary markdown without sanitization; probe output crafted to contain markdown or shell metacharacters can corrupt the summary or inject content visible to downstream consumers.
- [low] plugins/agent/validate/plugin.sh:130 — Clamping \`return "$hc_rc"\` to \`return 1\` silently discards probe-specific exit codes; if the health-check plugin uses distinct codes to signal security-relevant conditions (e.g. credential error vs. network timeout), callers lose that signal and cannot differentiate failure causes.

#### scope (score: 7/10)
- [medium] config/templates/deployed.yaml — In planned scope but untouched — the integration test manually exports ZBUILD_STAGE_INPUTS before the validate call rather than having the template wire it, meaning production runs via deployed.yaml may not supply the env var the v2 plugin now requires.
- [low] core/pipeline/disposition.sh — In planned scope but untouched — if this file defines disposition constants or helpers that the new v2 'disposition' field depends on, the planned scope inclusion suggests a change was expected here.
- [low] scripts/lib/lint-disposition-words.sh — In planned scope but untouched — the v2 contract introduces a 'disposition' field with values (broken, complete) that lint tooling may need to recognise; no corresponding vocabulary update is present in the diff.
- [low] scripts/lib/lint-verdict-classify.sh — In planned scope but untouched — similar to lint-disposition-words.sh, the new disposition vocabulary may require a classifier update that the diff does not include.
- [low] tests/unit/sigpipe-antipattern-guard-test.sh — In planned scope but untouched — plugin.sh was modified and the SIGPIPE guard test was in scope, though no new SIGPIPE-prone patterns are visible in the diff.
- [low] docs/wiki/plugins/validate.md — In planned scope but untouched — the contract version changed from v1 to v2 (result_contract, disposition, ZBUILD_STAGE_INPUTS); wiki documentation drift is expected without this update.
- [low] docs/adr/ADR-054-stage-contract.md — In planned scope but untouched — may have been included for reference verification only; no change was required if the ADR already describes the v2 contract shape being implemented.
- [low] docs/adr/ADR-055-inter-stage-data-contract-v2.md — In planned scope but untouched — same as ADR-054: may be reference-only, but the planned scope inclusion implies a cross-check or amendment was anticipated.

#### security (score: 8/10)
- [low] plugins/agent/validate/plugin.sh:75 — The deploy_result path is read from the externally-supplied ZBUILD_STAGE_INPUTS JSON file via jq and used as a filesystem path without sanitization; an adversarially crafted stage-inputs.json could point this to any path, giving an existence oracle for arbitrary files via the -f check.
- [low] plugins/agent/validate/plugin.sh:47 — mkdir -p "$ZBUILD_ARTIFACT_DIR" is executed unconditionally when state_file is missing and ZBUILD_ARTIFACT_DIR is set; an attacker who controls that env var can cause arbitrary directory creation before any guard fires.

#### sre (score: 6/10)
- [medium] plugins/agent/validate/plugin.sh:118 — Failed-probe diagnostic output (hc_snippet, up to 500 chars) is written only to the markdown summary; the structured result JSON carries data:{} — any downstream consumer or alert that previously read 'detail' or 'rc' from validate-result.json now gets nothing, silently.
- [low] plugins/agent/validate/plugin.sh:44 — The error artifact on missing state_file is written only when ZBUILD_ARTIFACT_DIR is set; if that env var is absent the broken-disposition path produces no structured artifact, leaving the failure unobservable to any result-scraping consumer.
- [low] plugins/agent/validate/plugin.sh:72 — A valid but structurally wrong stage-inputs.json (no .inputs.deploy_result key) causes jq to return empty and the stage to fail as 'missing required input' — a new silent failure mode with no event emitted and no distinction from a truly absent file.
- [low] plugins/agent/validate/plugin.sh:51 — Return-code normalization (rc 2→1) removes the only signal that distinguished engine-contract violations from probe failures at the exit-code level; any caller or CI step that branched on rc==2 will silently lose that distinction with no migration path.

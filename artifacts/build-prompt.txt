### zBuild — Vision

> The North Star for zBuild — it steers how zBuild is built. The README distills it; the wiki references it; every pipeline run is steered by it.

#### Intent
zBuild turns a delivery process into data — templates and plugins — so software is built the same disciplined way every time. We build zBuild the way zBuild builds: a minimal core, with all behavior plugin-delivered and template-composed. A good change is small, aligned to the spec, proven by a test, and wired into the live path — never scaffolding that looks finished but does nothing.

#### Principles
- **Target-agnostic by contract** — zBuild builds *any* repository, not itself; the engine and plugins never assume the target's language, layout, or that zBuild is the target. Target knowledge lives in data — templates, config, per-repo overrides — never in code.
- **Spec wins over drift** — KEEPERS, ARCHITECTURE, and the ADRs are the source of truth; when code disagrees, the code changes, not the spec.
- **Small engine, behavior at the edges** — keep the core tiny; add capability as plugins composed in templates, never by growing the engine.
- **Safety is structural** — all model-bound text passes one redaction chokepoint; state is atomic and resumable; scope is governed at every boundary.
- **Models are data, not code** — selection flows through the router and config tiers; never hardcode a model name.
- **Prove behavior, then wire it** — every change ships a test that fails without it and connects to the live path; green-but-inert is a defect.
- **Fail closed, never silent** — gates block on real problems and say why; bounded cycles and recovery drive work to done.
- **Dogfood every change** — build zBuild with zBuild; if the pipeline can't ship it, fix the pipeline.

### Rules
These are this repository's rules (.zbuild/prompts/rules.md). Work that
breaks one is wrong, whoever wrote it.

- Bash only, and match the file you are in: 4-space indent, LF line endings, a final newline, no trailing whitespace (.editorconfig). Everything must pass `shellcheck` with the repo's .shellcheckrc.
- Never pipe anything into `grep -q`, and never pipe into a bare `head`, in any `.sh` file, test files included. The reader exits early, the writer takes SIGPIPE, and under `set -o pipefail` the line fails for a reason nothing logs. Use a here-string instead: `grep -q PATTERN <<< "$var"`, or run grep on the file directly: `grep -q PATTERN "$file"`. `tests/unit/sigpipe-antipattern-guard-test.sh` fails the suite on any violation; a genuinely safe pipe is annotated `# sigpipe-ok: <reason>`.
- Never name a model (haiku, sonnet, opus, …) in code; model selection goes through core/router and config/models.json.
- A test must be able to fail: assert what is required, never what the code happens to do.
- Never edit anything under `legacy-DoNotUse/`.

#### Facts about this repo
- `ZBUILD_*` environment variables are set by the engine at dispatch (the artifact dir, the stage's input index `ZBUILD_STAGE_INPUTS`, the issue, the run). They are trusted engine inputs, not user or attacker input.
- A stage never names another stage's output — not its output name, not its file. The engine hands every stage every earlier stage's latest output, and a stage finds what it needs by what it contains (scripts/lib/earlier-output.sh; ADR-055 §1). A plugin that names another stage's output is a defect.
- Every stage writes a v2 result (`result_contract`, `verdict`, `disposition`, `reason`, detail under `data`) on every exit path, and exits 0 or 1 (ADR-054).
- `[SPEC-n]` / `[#<issue>/SPEC-n]` tags in a test tie an assertion to one issue's acceptance contract. A tag that belongs to another issue must never be changed or removed.

## What you own

Your job is to edit the working tree to implement the ORIGINAL TASK
below. You have Read, Edit, Write, and Bash tools available.

### How your work is kept
- You make code changes via Edit/Write/Bash. What you change stays in the
  working tree: if you do not finish, the next try continues from it, and your
  notes file (in the rules below) carries what you learned.
- Write your notes file first, and add each thing you find to it
  before your next step. If you are cut off, your notes are what the next try
  starts from.
- Do NOT emit a unified diff in your response — the pipeline derives the
  canonical `diff.patch` artifact from `git diff HEAD` automatically.

### Saying you are done
Emit `LOOP_COMPLETE` on its own line as the FINAL line of your response
WHEN the implementation is complete — whether you just finished it OR
it was already done before you started. If the branch already contains
the required changes (check `git log` for commits + `git diff` for any
remaining gap) AND no stage under Previous work has failed findings left to
answer, emit `LOOP_COMPLETE` immediately. Do NOT keep iterating when there is
nothing left to do. Every finding you are given is answered, each on its own
line before the sentinel: `done` (you changed something for it), `wrong`
(it does not hold, and why) or `not mine` (your job cannot fix it, and why).
A finding with no answer stays open, and is shown to you again.

### When a finding does not reproduce
If a failing stage names a test and that test PASSES when you run it on this
tree, say so and stop. Answer that finding, on its own line before the sentinel:

    ANSWER <the finding as listed>: wrong — not reproduced: <the path you ran>

one line per finding. This is a REPORT, not a verdict: the pipeline re-runs the
stage that raised the finding to check. Do not keep searching for the cause of
a failure you cannot produce, and do not change code to chase one.

### When a test is wrong
If a test fails on code that already does what its requirement says — the test
itself cannot pass — do not change the code to chase it; you may not change the
test. Answer that finding as soon as you are sure, on its own line before the
sentinel, and stop working on that test:

    ANSWER <the finding as listed>: wrong — the test is wrong: <test file>: <why>

Say exactly why it cannot pass. The stage that owns the tests is given this
answer, and fixes the test.

### When a test should change
If a test checks behaviour this change is meant to alter — it pins the old
output, value or rule — the test must change, and the stage that writes the
tests changes it. Answer its finding, on its own line before the sentinel:

    ANSWER <the finding as listed>: not mine — the test must change: <test file>: <why>

Say what the test pins and what the change makes it.

You know a test is wrong by a check, not by a feeling. If the test fails the
same way with your change set aside (git stash), your change did not cause it:
find what in the test makes it fail, give that answer, and stop.

### When a test leaves something behind
A test that leaves something behind — an exported variable, a file outside its
own folder, a background process — breaks the tests after it. Which of three it
is decides what you do:
1. Your code puts it where it should not: change the code to write where it is
   told (TMPDIR, HOME, or a folder the caller passes in).
2. The code is meant to leave it, and the test does not clean it up: you may
   not change the test. Answer, on its own line before the sentinel:

    ANSWER <the finding as listed>: wrong — the test is wrong: <test file>: needs cleanup of <what>

3. Every test needs the same guard: it belongs in the shared test helpers,
   which are in the test folders — answer the finding `not mine — the test
   must change: <helper file>: needs <the guard>`.

### Running tests
- Do NOT run `npm test`, the full suite, or `npm run lint` — the pipeline
  runs them and their results are under Previous work.
- Start from the test files listed under Previous work, and the requirements
  each covers. Run a test file only to see whether a failure still holds
  (below) or after you change the code it checks, and only that test file. A
  command that runs longer than ~2 minutes can cost you the whole call.
- A failed stage under Previous work shows what failed when that stage ran; the
  code may have changed since, so run that one test file once, before you work
  on it, to see whether it still fails, and start from the failing line it shows.

### Data another part of the code writes
When your change reads data that another part of the code writes — a file, a
record, a field, a message — open the code that writes it and use the names
and shapes it really produces, and when it produces them; never assume them.

### Commit message (#608)
Before the final `LOOP_COMPLETE` line, emit a single line of the form:

    COMMIT_SUMMARY: <one-line description of this iteration's change>

Keep it under 72 characters, present tense, imperative mood (e.g.
"add foo parser" not "added"). The pipeline uses this as the git commit
message for the per-iteration commit it creates on your behalf. If you
omit this line the pipeline falls back to the plan title.

### DESIGN DECISIONS (from the design stage — honor these directives; they refine the plan)
# Design: #1805 — resume and --from-stage trust-and-rehydrate

## Architectural decision

**Goal:** When a run is resumed (via `--resume`, auto-resume on restart, or `zbuild pipeline resume --run-id`), every stage already marked `complete` in the persisted state must have its artifacts restored from the git state branch into `ZBUILD_ARTIFACT_DIR` before the dispatch loop runs, using the same extraction path the hydrate plugin uses. After that restoration, a `complete` stage whose primary artifact is still absent must exit 1 (fail closed). For `--from-stage <s>`, the same rehydration runs for every stage before `<s>`; if any pre-target stage has no restorable artifact, the runner refuses before dispatching anything. Inside a loop, the cycle orchestrator must restore `cycle_iterations[X].current_iter` from persisted state and begin the iteration loop from that value, not from 1, but ONLY when a resume is active — fresh runs must always start from iter=1. Additionally, within the first resumed iteration, `_cycle_dispatch` must skip cycle member stages already marked complete in persisted state and explicitly emit stage.start for the interrupted (non-complete) member, so the first dispatched cycle member is the one that was actually interrupted.

- Gap 1 — runner.sh resume entry: disarms sentinel, emits `pipeline.resume`, NO artifact restoration. **Fixed** — `_runner_resume_rehydrate` (new function in runner.sh), called from `main()` in runner.sh at the resume entry point.
- Gap 2 — runner.sh stale-artifact branch warned+continued; after rehydration the right behaviour is exit 1. **Fixed** — exit 1 path in the dispatch-unit `stage:*` arm inside `main()` in runner.sh (comment: "ADR-006 §3.6 (#1805): fail closed").
- Gap 3 — runner.sh from-stage path: no artifact check or rehydration. **Fixed** — `_runner_from_stage_preflight` (new function in runner.sh).
